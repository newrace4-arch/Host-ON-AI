## 프로젝트

**Host ON (AI)** — 서로 다른 숙박업 유형(도시민박·호스텔 등)을 여러 개
운영하는 **1인 멀티호스트**를 위한 숙소 운영 자동화 서비스입니다.
개발자 본인이 3룸 독채(통대여)와 호스텔 객실을 실제로 운영하고 있고,
그 운영 형태가 아래 설계 선택 대부분의 출발점입니다.

- PostgreSQL 17 / SQLAlchemy 2.0 / FastAPI
- **16개 테이블**, 현재 스키마 v1.3 (Schema Freeze 상태)
- 구현 진행: 스키마·예약 서비스·채널 연동 완료, AI 응대/정산은 예정

## 16테이블 FK 관계도

```
hosts ─┬─< properties ─┬─< rooms ─< beds
       │               ├─< channel_connections
       │               ├─< financial_configs      [UNIQUE property_id → 1:1]
       │               ├─< monthly_settlements
       │               ├─< knowledge_chunks
       │               ├─< checklist_items
       │               ├─< inquiries              [단독FK + 복합FK 이중]
       │               ├─< action_items           [단독FK + 복합FK 이중]
       │               └─< reservations
       │                     ├─(room_id, property_id)─────────────> rooms   [복합]
       │                     ├─(bed_id, room_id)─────────────────> beds     [복합]
       │                     └─(channel_connection_id, property_id)> channel_connections [복합]
       │
       └─< inquiry_approvals.approved_by

reservations ─┬─< cleaning_tasks   [복합FK, UNIQUE reservation_id → 1:1]
              ├─< inquiries        [복합FK, ON DELETE CASCADE]
              └─< action_items     [복합FK, ON DELETE SET NULL (reservation_id)]

inquiries ─┬─< inquiry_classifications  [UNIQUE inquiry_id → 1:1]
           └─< inquiry_responses ─< inquiry_approvals

knowledge_chunks   ← FK로 참조하는 테이블이 없음 (1번 항목)
```

- 복합 FK **6개**, 단독 FK 11개. `hosts`만 FK 없음
- **16개 테이블 모두 단일 대리키(`BIGSERIAL`)를 PK로 사용**

# 1. INQUIRY_RESPONSES.sources — N:N을 JSONB 배열로 **[미기록]**

**현재 설계**
AI 응답이 어느 지식조각(`KNOWLEDGE_CHUNKS`)을 근거로 삼았는지를
`sources JSONB` 한 컬럼에 배열로 저장합니다 (실제 값: `["chunk_17"]`).

**그렇게 한 이유**
**미기록.** 명세서 2.12절이 컬럼을 선언만 하고, 왜 중간 테이블이 아닌지
설명이 없습니다. `sources`가 무엇을 담는지조차 DDL이 아니라 API 문서의
응답 예시에서만 확인됩니다.

**교재 기준으로 걸리는 점**
세 가지가 동시에 걸립니다.

| 관점 | 걸리는 점 |
|---|---|
| 1NF | 한 셀에 여러 값이 들어갑니다 |
| N:N | 응답 ↔ 지식조각은 명백한 N:N인데 중간 테이블이 없습니다 |
| 참조 무결성 | `KNOWLEDGE_CHUNKS`를 FK로 참조하는 테이블이 **16개 중 하나도 없습니다.** 청크가 삭제·재생성돼도 `"chunk_17"`은 그대로 남아 끊어진 참조가 됩니다 |

**▶ 검토받고 싶은 것**

1. "AI가 인용한 근거"처럼 **항상 응답과 함께 조회하고 개별 검색은 하지
   않는** 관계도 중간 테이블(`response_sources(response_id, chunk_id)`)로
   풀어야 합니까?
2. 조회 패턴이 단순하다는 이유가 JSONB를 정당화할 수 있습니까, 아니면
   **N:N은 예외 없이 중간 테이블**입니까?

> **이 항목을 1번에 둔 이유**: 나머지 항목은 이미 구현됐거나 근거 문서가
> 있는데, 이 부분은 **RAG 구현이 9/18~19라 아직 손대지 않았습니다.**
> 지금 답을 얻으면 그대로 만들면 되고, 나중에 얻으면 만든 것을 고쳐야
> 합니다.

# 2. RESERVATIONS.room_id·bed_id 둘 다 nullable

**현재 설계**
PROPERTY(독채 통대여) / ROOM(객실) / BED(도미토리 침대) **세 판매단위를
한 테이블**로 표현하고, `CHECK` 제약으로 3가지 유효 조합만 허용합니다.

```
(room_id NULL, bed_id NULL)  독채 전체 예약
(room_id 있음, bed_id NULL)  객실 단위 예약
(room_id 있음, bed_id 있음)  침대 단위 예약
```

**그렇게 한 이유**
명세서 0절 결정1·3, 2.6.1절. *"서로 다른 숙박업 유형을 여러 개 운영하는
1인 멀티호스트"*가 이 서비스의 차별점이라, 독채와 호스텔을 **하나의 구조로
동시에 표현**해야 했습니다.

**교재 기준으로 걸리는 점**

- 행마다 쓰이지 않는 컬럼이 생깁니다(독채 예약은 두 컬럼 모두 NULL).
  단위별로 테이블을 나누는 것이 정석으로 보입니다.
- **더 걸리는 점**: 판매단위를 결정하는 `bookable_unit_type`은
  `PROPERTIES`에 있고 `room_id`/`bed_id`는 `RESERVATIONS`에 있습니다.
  PostgreSQL 일반 CHECK는 다른 테이블을 참조할 수 없어 **이 교차 검증을
  DB가 못 합니다.** 애플리케이션 트랜잭션이 책임집니다.
  → **무결성의 일부를 DB 밖으로 내보낸 설계**입니다.
- 예약 기간 겹침 방지도 단위별로 `EXCLUDE` 제약을 **3개로 나눠** 걸었고,
  단위를 넘나드는 충돌(독채 예약 ↔ 그 하위 객실 예약)은 다시 애플리케이션이
  막습니다.

**▶ 검토받고 싶은 것**

1. "단일 테이블 + CHECK"와 "단위별 테이블 분리"를 가르는 **실무 기준**이
   무엇입니까?
2. 분리했다면 이 복잡도가 **줄었을까요**, 아니면 3개 테이블을 UNION으로
   조회하는 복잡도로 **옮겨갔을 뿐일까요**?
3. **DB가 검증할 수 없는 규칙을 애플리케이션에 맡기는 것**이 어디까지
   허용됩니까? 이 설계에서 그 경계가 적절합니까?

# 3. 계산할 수 있는 값을 저장한 두 층위 **[일부 미기록]**

**현재 설계**
성격이 다른 두 가지가 있습니다.

```
(가) RESERVATIONS.net_amount        = gross_amount - fee_amount
(나) MONTHLY_SETTLEMENTS 전체        = RESERVATIONS 집계 + 요율 복사
     ├ total_reservations / occupied_nights / occupancy_rate / gross_revenue
     └ applied_commission_rate      ← FINANCIAL_CONFIGS.commission_rate 복사
```

**그렇게 한 이유**

- **(나)는 근거가 명확합니다.** 명세서 2.8절 제목부터 *"FINANCIAL_CONFIGS와
  직접 관계 없음 — 스냅샷"*이고, 주석에 *"계산 당시 수수료율 스냅샷(설정이
  변경돼도 과거값 불변)"*이라고 적혀 있습니다. **FK를 의도적으로 끊었습니다.**
  수수료율을 나중에 바꿔도 지난달 정산서 금액이 달라지면 안 되기 때문입니다.
- **(가)는 미기록.** `net_amount`를 왜 저장하는지 어디에도 없습니다.

**교재 기준으로 걸리는 점**
"근거 없는 반정규화 금지" 원칙에 (가)가 직접 걸립니다. 단순 뺄셈이라
조회 시점에 계산해도 비용이 거의 없습니다.

**▶ 검토받고 싶은 것**

1. **"과거 시점 값의 불변 보존"**이 반정규화의 정당한 근거로 인정됩니까?
   (나)를 이 근거로 설명할 수 있습니까?
2. 그렇다면 **(가)와 (나)는 같은 반정규화가 아닌데**, (가)처럼 근거를 댈 수
   없는 중복은 제거하는 것이 맞습니까?
3. 반정규화를 할 때 **그 근거를 어디에 남기는 것이 실무 관행**입니까?
   (DDL 주석 / 별도 설계문서 / 코드)

# 4. 1:1 관계가 세 곳인데 기준이 서로 다릅니다 **[일부 미기록]**

**현재 설계**
1:1을 별도 테이블로 분리한 곳이 세 곳이고, 분리 근거가 제각각입니다.

| 관계 | 강제 방법 | 분리한 이유(문서 기준) |
|---|---|---|
| CLEANING_TASKS ↔ RESERVATIONS | `UNIQUE(reservation_id)` | 명시됨 — 청소는 5단계 상태머신을 갖고 예약과 생명주기가 다름 |
| INQUIRY_CLASSIFICATIONS ↔ INQUIRIES | `UNIQUE(inquiry_id)` | *"1문의=Claude 1회 통합호출 아키텍처와 일치"* — **왜 분리했는지에 대한 답은 아님** |
| **FINANCIAL_CONFIGS ↔ PROPERTIES** | `UNIQUE(property_id)` | **미기록** |

특히 `FINANCIAL_CONFIGS`는 컬럼 8개(수수료 유형·수수료율·기본 단가·VAT
포함 여부 등)로 **`PROPERTIES`에 그대로 합칠 수 있어 보이는데** 근거가 전혀
없습니다.

**교재 기준으로 걸리는 점**
1:1이면 한 테이블로 합치는 것이 기본입니다. 세 곳 모두 합치지 않았고,
그 이유가 서로 다릅니다.

**▶ 검토받고 싶은 것**

1. 1:1을 **별도 테이블로 두는 판단 기준**은 무엇입니까?
   "컬럼 수" / "NULL이 많이 생김" / "생명주기가 다름" / "접근 빈도가 다름"
   중 실무에서 결정적인 것은 어느 것입니까?
2. 같은 1:1인데 셋을 **다른 이유로** 분리했습니다. 일관된 기준 하나로
   설명할 수 있어야 합니까, 관계마다 다른 이유로 판단하는 것이 정상입니까?
3. `FINANCIAL_CONFIGS`는 근거가 없는데, **지금이라도 `PROPERTIES`에
   합치는 것이 맞습니까?**

# 5. INQUIRY_RESPONSES.is_latest — 계산할 수 있는 플래그

**현재 설계**
AI 응답 재시도·재답변 이력을 1:N으로 쌓고, 어느 것이 최신인지를
`is_latest BOOLEAN`으로 표시합니다. **부분 유니크 인덱스**로 문의 하나당
`is_latest = true`인 행이 **정확히 하나**임을 DB가 강제합니다.

```sql
CREATE UNIQUE INDEX uniq_inquiry_latest_response
  ON inquiry_responses(inquiry_id) WHERE is_latest = true;
```

**그렇게 한 이유**
명세서 0절 결정6, 2.12절. 재시도 상한은 2회(문의 1건당 AI 호출 최대 3회)로
정해져 있고, 호스트가 이전 응답도 볼 수 있어야 합니다.

**교재 기준으로 걸리는 점**
`is_latest`는 `MAX(created_at)`으로 **계산할 수 있는 값**입니다. 저장하면
중복이고, 갱신을 빠뜨리면 실제와 어긋납니다.

**▶ 검토받고 싶은 것**

1. 계산 가능한 플래그를 저장하는 것이 정규화 위반입니까, 아니면
   **부분 유니크 인덱스로 "최신은 하나뿐"이라는 불변식을 DB가 강제하면**
   허용되는 반정규화입니까?
2. 이 둘을 가르는 기준이 있습니까?

# 6. INQUIRIES.channel — 같은 개념인데 타입이 다르고 FK가 없습니다 **[미기록]**

**현재 설계**

```sql
channel_connections.channel   channel_enum    -- 'AIRBNB' | 'BOOKING_COM' | 'NAVER'
inquiries.channel             VARCHAR(30)     -- 자유 문자열, FK 없음
```

같은 "채널"인데 한쪽은 ENUM, 한쪽은 자유 텍스트입니다. `INQUIRIES`는
`CHANNEL_CONNECTIONS`를 참조하지 않습니다.

**그렇게 한 이유**
**미기록.**

**교재 기준으로 걸리는 점**
같은 도메인 값을 두 곳에서 다른 타입으로 관리하고 있고, 참조 무결성이
없어 오타나 표기 흔들림("airbnb" / "Airbnb" / "에어비앤비")을 막을 수단이
없습니다.

**▶ 검토받고 싶은 것**

문의는 채널 연동이 없는 경로(웹 폼, 전화, 직접 문자)로도 들어올 수 있어
FK를 걸기 어려운 것으로 보입니다. 이럴 때 어느 쪽이 맞습니까?

1. ENUM으로 통일하고 `DIRECT` 같은 값을 추가한다
2. 자유 텍스트로 두되 입력값을 애플리케이션에서 정규화한다
3. nullable FK + 자유 텍스트를 병행한다(연동 채널이면 FK, 아니면 텍스트)

# 7. CHECKLIST_ITEMS.accommodation_type — 이름과 의미가 어긋납니다

**현재 설계**
숙박업 인허가 체크리스트 항목에 `accommodation_type`을 함께 저장합니다.
`property_id`가 있으므로 `PROPERTIES.accommodation_type`을 따라갈 수 있어,
겉보기에는 **3NF 이행 종속**입니다.

**그렇게 한 이유**
명세서 0절 결정10에 근거가 있습니다 — *"파생 템플릿 유형을 의미(Property
현재 유형의 실시간 복사본이 아님)"*. 즉 **숙소 유형이 나중에 바뀌어도 이미
발급된 체크리스트는 발급 당시 유형을 유지**해야 한다는 뜻입니다.
(3번의 "시점 스냅샷"과 같은 성격입니다.)

**교재 기준으로 걸리는 점**
근거는 있지만 **컬럼 이름이 그 의도를 전혀 전달하지 못합니다.**
`accommodation_type` 하나만 보면 누구든 `PROPERTIES`의 복사본으로 읽고,
"중복이니 지우자"고 판단할 수 있습니다.

**▶ 검토받고 싶은 것**

1. 의미가 다르다는 것을 **컬럼 이름으로 구분**해야 합니까?
   (`template_accommodation_type` 등)
2. 아니면 주석·설계문서로 남기는 것으로 충분합니까?
3. 일반적으로 **"스냅샷 값"임을 스키마에서 드러내는 관행**이 있습니까?

| 10 | 복합 FK를 6곳에 쓴 것 | 다른 숙소의 예약·객실을 잘못 참조하는 일을 DB가 막도록 `(reservation_id, property_id)` 형태의 복합 FK를 6곳에 걸었습니다. 이 방식이 과한 편입니까? |
| 11 | `RESERVATIONS` 컬럼 21개 | 예약 상태 3종(예약/환불/정산)과 금액 3종, 정산 예정일·실제일이 한 테이블에 있습니다. 테이블을 쪼갤 기준이 있습니까? |

## 검토 결과 문제가 없다고 판단한 것

억지로 개수를 채우지 않기 위해, **문제를 찾지 못한 항목도 함께 적습니다.**

| 정규형 | 판단 | 근거 |
|---|---|---|
| **제2정규형** | 위반이 **구조적으로 불가능** | 16개 테이블 전부 **단일 대리키**를 PK로 씁니다. 부분 종속은 복합 **기본키**에서만 생기는데 복합 PK가 하나도 없습니다. (복합 **FK**는 6곳 있지만 PK가 아니라 2NF 대상이 아닙니다.) |
| **제4정규형** | 위반 **없음** | 다중값을 담은 컬럼이 `photo_urls`·`sources` 둘인데 **서로 다른 테이블**에 있습니다. 한 테이블에 독립적인 다중값이 둘 이상 섞인 경우가 없습니다. |
| **N:N 직접 연결** | **1건**(위 1번)뿐 | 나머지 관계는 모두 1:N으로 분해돼 있습니다. |

**이 판단 자체가 맞는지도 함께 확인받고 싶습니다.**

## 카테고리 1: DB & 데이터 무결성 설계 결함

### 1. 예약 겹침방지 제약을 하나로 통합하려다 데이터 오염 위험 발견

**문제**: PROPERTY(독채)/ROOM/BED 세 가지 예약 단위의 기간 겹침을 하나의
PostgreSQL `EXCLUDE` 제약으로 통합하기 위해 `COALESCE(room_id, 0)` 방식을
검토했다.

**원인**: `room_id`가 `NULL`인 경우(독채 예약)와 실제로 `room_id`가 0번인
경우를 시스템이 구분하지 못해, 서로 다른 예약 단위임에도 같은 값으로
취급되어 데이터가 오염될 위험이 있음을 발견했다.

**해결**: PROPERTY/ROOM/BED 단위별로 `EXCLUDE` 제약을 3개로 분리했다.
서로 다른 예약 단위 간의 교차 충돌(예: 독채 예약과 그 하위 객실 예약이
동시에 존재하는 경우)은 DB 제약만으로 해결할 수 없어, 애플리케이션
트랜잭션 레벨에서 별도로 검증하도록 역할을 분리했다.

### 2. "DB가 자동으로 강제한다"고 설계했던 규칙이 기술적으로 불가능했음을 발견

**문제**: `Property.bookable_unit_type`(판매 단위: PROPERTY/ROOM/BED)과
`Reservation`의 실제 `room_id`/`bed_id` 사용 형태가 일치하는지를 DB
`CHECK` 제약 하나로 강제하도록 설계했었다.

**원인**: `bookable_unit_type`은 `PROPERTIES` 테이블에, `room_id`/
`bed_id`는 `RESERVATIONS` 테이블에 있는데, **PostgreSQL의 일반 CHECK
제약은 다른 테이블의 값을 참조할 수 없다**는 기술적 한계를 뒤늦게
확인했다.

**해결**: DB CHECK는 같은 행(row) 내부의 형태(`room_id`/`bed_id` 조합이
유효한 3가지 패턴 중 하나인지)만 검증하도록 범위를 한정했다. `Property`와의
교차 일치 여부, 즉 `bookable_unit_type ↔ room_id/bed_id` 의미론적 검증과
Property 소유권 확인은 FastAPI 서비스 계층(Pydantic Validator + 예약
생성 트랜잭션 사전검증)에서 400 에러로 차단하도록 책임을 명확히
분리했다.

### 3. 게스트 문의-응답을 1:1로 설계했다가 재시도 시나리오 누락 발견

**문제**: "게스트 문의 1건 = AI 응답 1건"이라는 가정으로 `INQUIRIES`와
`INQUIRY_RESPONSES`를 1:1 관계로 설계했다.

**원인**: 실제로는 LLM API 호출 실패 후 재시도, 호스트가 AI 초안을
마음에 안 들어해서 재생성 요청, 승인 거부 후 재작성 등 **한 문의에
응답이 여러 번 생성되는 시나리오**가 존재함을 확인했다. 1:1 구조로는
이런 경우 DB 오류(UniqueViolation)로 시스템이 멈추는 문제가 있었다.

**해결**: 1:N 관계로 재설계하고 `is_latest`(최신응답) 플래그를
추가했다. 문의당 "최신 응답"이 정확히 1개만 존재하도록 부분 UNIQUE
인덱스(`WHERE is_latest = true`)로 강제하되, 과거 응답 이력은 삭제하지
않고 보존하도록 했다.

### 4. 정산 결과가 수수료 설정값 변경에 영향받는 회계 원칙 위반 위험 발견

**문제**: 월별 정산 결과(`MONTHLY_SETTLEMENTS`)가 수수료 설정
(`FINANCIAL_CONFIGS`)을 직접 외래키로 참조하도록 설계했다.

**원인**: 이후 수수료율이 변경되면, 이미 확정된 과거 정산 결과까지
새 수수료율의 영향을 받게 되는 회계 원칙 위반 상황이 발생할 수 있음을
발견했다(예: 9월 정산을 10월에 다시 조회했을 때 계산 당시와 다른
값이 나오는 문제).

**해결**: 직접 외래키 연결을 제거하고, 정산 계산 시점의 수수료율을
`applied_commission_rate` 컬럼에 스냅샷(복사)으로 저장하도록
변경했다. 이후 설정값이 바뀌어도 과거 정산 기록은 영향받지 않는다.

### 5. 청소작업 생성 시점을 "체크아웃"으로 설계했다가 다른 확정기능과 모순 발견

**문제**: `CLEANING_TASKS`를 예약의 체크아웃 시점(당일)에 생성하도록
설계했었다.

**원인**: 이미 확정되어 있던 "청소 전날·당일 청소도우미 자동알림"
기능과 논리적으로 충돌함을 뒤늦게 발견했다. 청소작업 레코드가
체크아웃 당일에야 생성된다면, "전날" 알림을 보낼 대상 자체가 DB에
존재하지 않아 그 기능이 물리적으로 성립할 수 없었다. 당근마켓 등
비정규 청소인력의 노쇼를 방지하려던 원래 목적과 정반대의 결과였다.

**해결**: 청소작업의 **생성 시점**과 **실제 실행 시점**을 분리했다.
예약이 `CONFIRMED` 상태로 전이되는 즉시 `scheduled_date`(체크아웃일)를
지정해 청소작업을 선제 생성하고, 실제 청소 착수는 여전히 체크아웃
당일 그대로 진행한다. 이로써 사전 알림 기능이 논리적으로 성립하게
되었고, 호스트 입장에서도 예약이 들어오는 즉시 청소 일정을 미리
확인할 수 있게 되었다.

### 9. 같은 필드를 두 문서가 정반대로 규정하고 있었음 (NOT NULL vs Optional)

**문제**: 9/4 1단계 검증에서, `INQUIRIES.reservation_id`를 DB 명세서는
`NOT NULL`로, API Contract는 "Optional(예약 전 사전문의 지원)"으로
규정하고 있는 정면 충돌을 발견했다. 더 나쁜 것은 API Contract가
**"DB도 nullable로 설계되어 있음(명세서 2.10절)"이라고 명세서를 잘못
인용**하고 있어서, 읽는 사람이 충돌 자체를 알아채기 어려웠다는 점이다.

**원인**: "예약 전 사전문의" 기능은 API 설계 단계에서 뒤늦게 추가된
요구사항인데, 그때 DB 명세서까지 되돌아가 고치지 않고 API 문서에만
반영했다. 9/5에 이 상태로 구현했다면 사전문의 INSERT가 NOT NULL 위반으로
전부 실패했을 것이다.

**해결**: 사전문의 기능을 유지하기로 결정하고 DB 쪽을 nullable로
변경했다. 이때 **PostgreSQL 복합 FK의 `MATCH SIMPLE` 동작**(구성 컬럼 중
하나라도 NULL이면 FK 검사를 통째로 스킵)을 확인해, `reservation_id`가
NULL인 사전문의 행에서는 `property_id`가 존재하지 않는 숙소여도 INSERT가
통과한다는 2차 구멍까지 발견했다. 이를 막기 위해 `property_id`에 **단독
FK를 추가로 신설**했다(단독FK = "이 숙소가 실재하는가", 복합FK = "이
예약이 정말 이 숙소의 예약인가"로 역할 분리).

### 10. 저장할 컬럼이 없는 API가 2개 존재했음

**문제**: API Contract에 `GET /channels/{id}/sync-errors`(동기화 실패
사유 조회)와 `POST /cleaning-tasks/{id}/photo`(청소 완료사진 업로드)가
정의돼 있는데, 그 데이터를 담을 컬럼이 DB 명세서 어디에도 없었다.

**원인**: API를 먼저 설계하고 스키마 반영을 나중으로 미루면서 누락됐다.
두 기능 모두 실행 체크리스트(9/13 채널연결 실패 UI, 10/3 사진업로드
VERIFIED)에 확정 작업으로 올라가 있어, 해당 날짜에 가서야 "저장할 데가
없다"는 것을 발견했을 상황이었다.

**해결**: 새 테이블을 만들지 않고 컬럼 2개만 추가했다.
`CHANNEL_CONNECTIONS.last_error_message`(TEXT, 마지막 1건만 보관하고
동기화 성공 시 NULL로 초기화)와 `CLEANING_TASKS.photo_urls`(JSONB 배열,
교체가 아니라 append 누적). 동시에 **"API Contract에 엔드포인트를 새로
적을 때는 저장할 컬럼이 명세서에 있는지 먼저 확인한다"**를 `CLAUDE.md`
규칙으로 명문화해 재발을 막았다.

### 11. 액션아이템이 다른 숙소의 예약을 참조할 수 있는 구멍

**문제**: `ACTION_ITEMS`는 `property_id`와 `reservation_id`를 각각
**서로 무관한 단독 FK**로 갖고 있었다. 그래서 "강남 숙소의 액션아이템인데
참조하는 예약은 홍대 호스텔 예약"인 행이 DB 레벨에서 아무 저항 없이
만들어질 수 있었다.

**원인**: `CLEANING_TASKS`와 `INQUIRIES`에는 계층 무결성을 위한 복합 FK를
걸어뒀으면서, 나중에 추가된 `ACTION_ITEMS`에는 같은 방어를 적용하지
않았다. 이 프로젝트의 최상위 원칙이 "Property 단위 데이터 격리"인데
정작 모든 알림이 모이는 단일 지점에 구멍이 있었던 셈이다.

**해결**: `FOREIGN KEY (reservation_id, property_id)` 복합 FK로 전환했다.
`RESERVATIONS`에 이미 `UNIQUE(reservation_id, property_id)`가 있어 추가
제약 없이 참조가 가능했다. 다만 기존 삭제 정책이 `ON DELETE SET NULL`
이었는데, 복합 FK에서 컬럼 목록 없이 `SET NULL`을 쓰면 `NOT NULL`인
`property_id`까지 NULL로 만들려다 **삭제 자체가 실패**한다는 점을 확인해,
PostgreSQL 15+의 `ON DELETE SET NULL (reservation_id)` 문법으로 명시했다.
이에 따라 로컬 Docker 이미지도 PG15 이상으로 고정하기로 했다.

### 12. 실행 지시서가 명세서 개정을 따라가지 못해 필드 2개가 빠질 뻔함

**문제**: 9/5에 그대로 복사해 실행할 `claude_code_stage1_schema.md`
지시서의 `PROPERTIES` 컬럼 목록에 `weekday_adjustment_enabled`와
`holiday_adjustment_enabled`가 없었다.

**원인**: 이 지시서는 명세서 **v1.1 시점**에 작성됐는데, v1.2에서 동적
가격조정 기능을 추가하며 위 두 필드를 명세서에만 넣고 지시서는 갱신하지
않았다. 그대로 실행했다면 필드 2개가 빠진 채 테이블이 만들어지고,

**해결**: 지시서에 두 필드와 `lower_bound_price`를 보완하고, Schema
Freeze 통과 기준에도 확인 항목으로 추가했다. 근본 원인은 "SSOT를 고칠 때
그것을 인용하는 파생 문서까지 함께 고치는 절차가 없었다"는 것이므로,
이후 3문서 기계 대조(컬럼명 diff 스크립트)를 검증 절차에 포함시켰다.
같은 검증에서 ERD 물리 스키마에 컬럼 25개가 누락돼 있던 것도 함께
발견해 보충했다.

### 13. SQLAlchemy가 PostgreSQL 15 전용 `ON DELETE SET NULL (컬럼목록)`을 렌더링하지 못함 (9/5 구현)

**문제**: 명세서 2.15절이 요구하는 `ACTION_ITEMS`의 복합FK
`ON DELETE SET NULL (reservation_id)`를 SQLAlchemy 모델에
`ondelete="SET NULL (reservation_id)"`로 그대로 적으면 테이블 생성 시점에
`CompileError: Unexpected SQL phrase`로 실패한다.

**원인**: SQLAlchemy 2.0.35는 FK의 `ondelete` 문자열을
`^(?:RESTRICT|CASCADE|SET NULL|NO ACTION|SET DEFAULT)$` 정규식으로 검증한다.
PostgreSQL 15에서 추가된 **컬럼목록을 지정하는 SET NULL 문법을 아직
지원하지 않는다.** 그렇다고 컬럼목록 없이 `SET NULL`만 쓰면, 예약 삭제 시
NOT NULL인 `property_id`까지 NULL로 만들려다 **삭제 자체가 실패**한다.

**해결**: 모델에는 표준 `SET NULL`로 선언해 DB 리플렉션과 값이 일치하도록
두고(그래야 이후 `alembic check`가 매번 차이를 보고하지 않는다), 실제 컬럼목록
문법은 두 경로 모두에 적용했다 — ① 모델 파일의 `after_create` DDL 이벤트
(`create_all` 경로), ② 초기 마이그레이션의 `op.execute` ALTER(Alembic 경로).
적용 결과는 `pg_constraint.confdelsetcols`가 `reservation_id` 컬럼만 가리키는지로
검증했고, 실제 예약 삭제 후 `reservation_id`만 NULL이 되고 행은 남는 것을 확인했다.

### 14. autogenerate가 pgvector import와 확장 생성문을 누락 (9/5 구현)

**문제**: `alembic revision --autogenerate`로 생성된 초기 마이그레이션을
그대로 `upgrade`했다면 `NameError: pgvector`와 `type "vector" does not exist`로
실패했을 것이다.

**원인**: autogenerate는 컬럼 타입을 `pgvector.sqlalchemy.vector.VECTOR(dim=384)`로
렌더링하면서도 해당 **import 문은 넣어주지 않으며**, `CREATE EXTENSION`
(`vector`, `btree_gist`)은 애초에 모델 메타데이터에 없는 정보라 생성 대상이 아니다.

**해결**: CLAUDE.md 코딩규칙 10번("생성된 파일을 바로 upgrade하지 말고 먼저
검토")대로 파일을 먼저 열어 확인하고 import 1줄과 확장 생성 2줄을 수동 추가했다.
downgrade에는 ENUM 15종 `DROP TYPE`도 함께 추가했다(테이블만 지우면 타입이 남아
재적용 시 "type already exists"로 실패). 한편 **가장 누락을 걱정했던 EXCLUDE 3종과
부분 UNIQUE 인덱스는 autogenerate가 정상적으로 잡아냈다** — 모델에
`postgresql.ExcludeConstraint`로 선언해두면 인식된다.

### 15. 지시서가 전제한 "backend 골격"이 실제로는 비어 있었음 (9/5 구현)

**문제**: 실행 지시서는 "이미 골격이 있는 폴더에 모델 파일만 작성"과
"전제조건: venv/Alembic/Docker Postgres 준비 완료"를 전제했으나, 실제
`backend/`에는 `.gitkeep` 하나뿐이었다.

**원인**: 8/31 이후 문서·설계 작업만 진행했고 실제 코드 착수가 9/5였기 때문에,
지시서를 쓸 당시 예상했던 준비 작업이 아직 수행되지 않은 상태였다.

**해결**: 모델 작성 전에 venv 생성 + 의존성 설치, `docker-compose.yml`
(pgvector/pgvector:pg16 — 명세서가 요구하는 PG15+ 충족, Supabase와 메이저 정합),
`app/core/config.py`·`database.py`, Alembic 초기화까지 함께 수행했다.
접속정보는 `alembic.ini`에 적지 않고 `.env` → `env.py` 주입 방식으로 통일해
자격증명이 커밋되지 않도록 했다. 또한 ENUM 15종이 여러 모델에서 공유되므로
(`accommodation_type_enum`은 PROPERTIES와 CHECKLIST_ITEMS 양쪽에서 사용)
지시서 매핑표에 없던 `app/models/enums.py`를 추가해 타입 객체를 한 곳에서만
정의하도록 했다 — 파일마다 따로 정의하면 같은 타입을 두 번 CREATE 하려다 실패한다.

### 16. 비동기 테스트가 개별 실행은 통과하는데 연속 실행하면 전부 깨짐 (9/5 구현)

**문제**: 예약 무결성 회귀 테스트를 작성해 실행하니 테스트 자체는 통과하는데
(`17 passed`) 두 번째 테스트부터 **teardown에서 전부 에러**가 났다
(`sqlalchemy.exc.MissingGreenlet`). 한 개만 따로 돌리면 멀쩡히 통과해서
원인이 바로 보이지 않았다.

**원인**: 두 가지가 겹쳐 있었다.
① pytest-asyncio는 테스트마다 **새 이벤트 루프**를 만드는데, 앱의 공용 엔진
(`app/core/database.py`)은 커넥션 풀을 모듈 레벨에 들고 있다. 첫 테스트의
루프에 묶인 asyncpg 커넥션을 다음 테스트가 재사용하는 순간 깨진다.
② 정리(teardown) 코드에서 `await session.rollback()` 뒤에 `obj.host_id`를
읽었는데, rollback은 인스턴스 속성을 만료시키므로 이 접근이 **지연로딩(동기
IO)** 을 유발한다. async 컨텍스트에서 동기 IO를 하면 같은 예외가 난다.

**해결**: ① 테스트 세션은 `NullPool` 엔진으로 따로 만들어 커넥션을 재사용하지
않게 했고, ② PK를 rollback 전에 값으로 미리 뽑아두도록 고쳤다. 이후 18개
테스트가 연속 실행에서 전부 통과한다. **앞으로 추가할 비동기 테스트도 앱
공용 엔진을 그대로 쓰지 말 것** — 같은 증상이 반복된다.

### 17. 로컬 Postgres와 Supabase의 메이저 버전이 갈라져 있었음 (9/5)

**문제**: 9/5 스키마 구현 시 로컬 Docker 이미지를 `pgvector/pgvector:pg16`
으로 잡았는데, 이후 프로덕션 Supabase가 **PostgreSQL 17.6**임이 확인됐다
(Gemini 교차검증 완료). 로컬 16 / 운영 17로 메이저 버전이 갈라진 상태였다.

**원인**: 명세서 5절의 요구사항을 "15 이상이면 된다"로만 읽었기 때문이다.
그 조항의 실제 취지는 두 가지인데, 앞의 하나만 충족한 상태였다 —
① `ON DELETE SET NULL (컬럼목록)`이 PG15+ 전용이라 최소 15가 필요하다,
② **로컬 Docker와 Supabase를 같은 메이저로 맞춘다(dev/prod parity)**.
메이저가 다르면 예약 겹침방지에 쓰는 `EXCLUDE ... USING gist`, `tsrange`,
부분 UNIQUE 인덱스, pgvector 같은 요소가 로컬에서만 통과하고 배포에서
달라져도 발표 직전까지 모른 채 지나갈 수 있다.

**해결**: `docker-compose.yml` 이미지를 `pg17`로 올리고, 이미지만 바꾸는
데서 끝내지 않고 **빈 DB에서 스키마 전체를 다시 만들어** 재현되는지까지
확인했다(`docker compose down -v` → `alembic upgrade head`). PG17.11에서
16개 테이블 / ENUM 15종 / EXCLUDE 3종 / `confdelsetcols`(컬럼목록 SET NULL)
/ 확장 2종이 모두 그대로 생성됐고, 회귀 테스트 20개(예약 무결성 18 +
헬스체크 2)와 `alembic check`도 전부 통과했다. 마이그레이션 수정은
필요 없었다 — 즉 이번 건은 실제 장애가 아니라 **터지기 전에 막은 시한폭탄**
이었다.

**교훈**: 버전 제약을 "최소 몇 이상"으로만 기억하면 parity 요구를 놓친다.
로컬/운영 버전은 숫자를 직접 뽑아 **대조**해야 하고, 버전을 바꾼 뒤에는
반드시 빈 DB에서 마이그레이션을 다시 돌려봐야 한다.

## 카테고리 3: 인프라 및 개발 프로세스 통제

### 7. 무료 배포 환경의 Cold Start 리스크 확인 및 대안 인프라 검토

**문제**: 배포 플랫폼(Render) 무료 플랜의 특성을 사전에 충분히
검토하지 않은 상태였고, 이를 회피하기 위해 Hugging Face Spaces로의
배포처 전환도 함께 검토했다.

**원인**: Render는 15분간 요청이 없으면 서버가 슬립 상태로 전환되고,
이후 첫 요청에 최대 50초의 지연(Cold Start)이 발생함을 확인했다.
대안으로 검토한 Hugging Face Spaces는 2026년 7월부터 무료 Docker SDK
Space를 유료 등급으로 전환했고, 아웃바운드 네트워크가 1024번 이하
포트로 제한되어 있어 우리 서비스가 필수로 사용하는 외부 API(Claude
API, Supabase, iCal 등 대부분 443번 포트 사용)가 차단될 수 있음을
확인했다.

**해결**: 배포처는 Render를 그대로 유지하되, 배포 시점을 마감 직전이
아닌 **10/1로 조기화**하여 문제 발생 시 대응할 시간을 확보했고,
발표 직전 수동으로 서버를 깨우는 웨이크업 절차를 운영 규칙에
포함시켰다. Hugging Face는 원래 목적(로컬 임베딩 모델 다운로드)으로만
활용하기로 결정했다.

### 8. 여러 AI 도구를 동시에 활용하는 과정에서 예상되는 충돌 위험 사전 차단

**문제**: 설계 검토는 Claude와 Gemini 두 AI를 교차 활용하고 있었는데,
이 흐름이 실제 코드 편집까지 확장될 경우의 위험을 점검했다.

**원인**: 여러 AI에게 동시에 같은 코드 저장소의 파일 편집을 맡기면
Git 충돌, 서로의 변경사항을 모른 채 덮어쓰기, 코드 스타일 혼재
같은 문제가 발생할 수 있음을 사전에 인지했다.

**해결**: 개발자가 DB 명세서(`3rd_host_ai_db_spec_v1.md`)를 스키마의
단일 진실공급원(SSOT)으로 먼저 확정하고, 이를 기준으로 AI 도구 간
권한을 명확히 통제했다. Gemini는 검토·조사·지시서 작성 전용, Claude
Code는 실제 저장소 파일 수정·구현 전용으로 역할을 분리하여
`CLAUDE.md`/`GEMINI.md`에 명문화했다. 이를 통해 AI 도구 간 동시
편집으로 인한 파일 충돌과 설계 기준 불일치, 그리고 AI 생성 결과물의
환각(hallucination)을 개발자가 상위에서 통제하는 구조를 확립했다.

**추가 안정성 정책**: 같은 맥락에서, 게스트 문의 응대 AI Agent의
Claude 재호출도 무제한으로 열어두지 않았다. 호스트가 AI 초안을
거절하고 재생성을 요청하는 경우 **재시도 가능 횟수를 최대 2회로
제한**하여 문의 1건당 Claude 호출이 최대 3회(최초 1회+재시도 2회)를
넘지 않도록 통제했고, 재시도가 소진되면 호스트 수동 작성으로
자동 전환되도록 설계했다. 이는 `MAX_AGENT_STEPS`, API Spend Limit,
Rate Limit과 함께 다층으로 작동하여 비용 폭주 가능성을 원천 차단한다.

여러 차례 교차 검증(크로스체크)하는 과정에서 발견되어 사전에

문제들이며, 개발자가 AI 도구를 활용하면서도 설계 기준과 최종
의사결정을 주도적으로 수행했음을 보여준다.

**13~17번의 성격**: 반대로 이 5건은 설계가 아니라 **구현 도구의 한계와
실행 환경**에서
나왔다. 명세서가 요구한 PostgreSQL 15 문법을 ORM이 지원하지 않거나
(13번), 자동생성 도구가 일부 DDL을 빠뜨리는(14번) 경우로, 문서 대조로는
미리 잡을 수 없고 실제로 실행해봐야 드러난다. "자동생성 결과를 바로
적용하지 말고 먼저 검토한다"는 규칙이 실제로 사고를 막아준 사례다.
16번은 한 걸음 더 나아가, **테스트를 하나씩 돌리면 안 보이고 전부 돌려야
보이는 종류의 결함**도 있다는 것을 보여준다. 17번은 코드가 아니라
**실행 환경(로컬 DB 버전)이 운영과 어긋나 있던 경우**로, 문서의 버전
제약을 최솟값으로만 읽으면 놓치게 되는 유형이다.

**9~12번에서 얻은 교훈**: 문서가 늘어나면 "각 문서는 맞는데 서로
어긋나는" 오류가 생기고, 이것은 사람이 눈으로 읽어서는 잘 안 보인다.
그래서 1단계 검증에서는 **명세서의 `CREATE TABLE` 블록과 ERD의 엔티티
정의를 파싱해 컬럼명을 기계적으로 diff**하는 방식을 썼고, 그 결과
사람이 5번 읽어도 못 찾았던 누락 25건을 한 번에 찾아냈다. 이후 단계
검증에도 같은 방식을 적용한다.

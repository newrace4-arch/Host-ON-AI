## 카테고리 1: DB & 데이터 무결성 설계 결함

### 1. 예약 겹침방지 제약을 하나로 통합하려다 데이터 오염 위험 발견

**문제**: PROPERTY(독채)/ROOM/BED 세 가지 예약 단위의 기간 겹침을 하나의
PostgreSQL `EXCLUDE` 제약으로 통합하기 위해 `COALESCE(room_id, 0)` 방식을
검토했다.

**원인**: `room_id`가 `NULL`인 경우(독채 예약)와 실제로 `room_id`가 0번인
경우를 시스템이 구분하지 못해, 서로 다른 예약 단위임에도 같은 값으로
취급되어 데이터가 오염될 위험이 있음을 발견했다.

**해결**: PROPERTY/ROOM/BED 단위별로 `EXCLUDE` 제약을 3개로 분리했다.
서로 다른 예약 단위 간의 교차 충돌(예: 독채 예약과 그 하위 객실 예약이
동시에 존재하는 경우)은 DB 제약만으로 해결할 수 없어, 애플리케이션
트랜잭션 레벨에서 별도로 검증하도록 역할을 분리했다.

### 2. "DB가 자동으로 강제한다"고 설계했던 규칙이 기술적으로 불가능했음을 발견

**문제**: `Property.bookable_unit_type`(판매 단위: PROPERTY/ROOM/BED)과
`Reservation`의 실제 `room_id`/`bed_id` 사용 형태가 일치하는지를 DB
`CHECK` 제약 하나로 강제하도록 설계했었다.

**원인**: `bookable_unit_type`은 `PROPERTIES` 테이블에, `room_id`/
`bed_id`는 `RESERVATIONS` 테이블에 있는데, **PostgreSQL의 일반 CHECK
제약은 다른 테이블의 값을 참조할 수 없다**는 기술적 한계를 뒤늦게
확인했다.

**해결**: DB CHECK는 같은 행(row) 내부의 형태(`room_id`/`bed_id` 조합이
유효한 3가지 패턴 중 하나인지)만 검증하도록 범위를 한정했다. `Property`와의
교차 일치 여부, 즉 `bookable_unit_type ↔ room_id/bed_id` 의미론적 검증과
Property 소유권 확인은 FastAPI 서비스 계층(Pydantic Validator + 예약
생성 트랜잭션 사전검증)에서 400 에러로 차단하도록 책임을 명확히
분리했다.

### 3. 게스트 문의-응답을 1:1로 설계했다가 재시도 시나리오 누락 발견

**문제**: "게스트 문의 1건 = AI 응답 1건"이라는 가정으로 `INQUIRIES`와
`INQUIRY_RESPONSES`를 1:1 관계로 설계했다.

**원인**: 실제로는 LLM API 호출 실패 후 재시도, 호스트가 AI 초안을
마음에 안 들어해서 재생성 요청, 승인 거부 후 재작성 등 **한 문의에
응답이 여러 번 생성되는 시나리오**가 존재함을 확인했다. 1:1 구조로는
이런 경우 DB 오류(UniqueViolation)로 시스템이 멈추는 문제가 있었다.

**해결**: 1:N 관계로 재설계하고 `is_latest`(최신응답) 플래그를
추가했다. 문의당 "최신 응답"이 정확히 1개만 존재하도록 부분 UNIQUE
인덱스(`WHERE is_latest = true`)로 강제하되, 과거 응답 이력은 삭제하지
않고 보존하도록 했다.

### 4. 정산 결과가 수수료 설정값 변경에 영향받는 회계 원칙 위반 위험 발견

**문제**: 월별 정산 결과(`MONTHLY_SETTLEMENTS`)가 수수료 설정
(`FINANCIAL_CONFIGS`)을 직접 외래키로 참조하도록 설계했다.

**원인**: 이후 수수료율이 변경되면, 이미 확정된 과거 정산 결과까지
새 수수료율의 영향을 받게 되는 회계 원칙 위반 상황이 발생할 수 있음을
발견했다(예: 9월 정산을 10월에 다시 조회했을 때 계산 당시와 다른
값이 나오는 문제).

**해결**: 직접 외래키 연결을 제거하고, 정산 계산 시점의 수수료율을
`applied_commission_rate` 컬럼에 스냅샷(복사)으로 저장하도록
변경했다. 이후 설정값이 바뀌어도 과거 정산 기록은 영향받지 않는다.

### 5. 청소작업 생성 시점을 "체크아웃"으로 설계했다가 다른 확정기능과 모순 발견

**문제**: `CLEANING_TASKS`를 예약의 체크아웃 시점(당일)에 생성하도록
설계했었다.

**원인**: 이미 확정되어 있던 "청소 전날·당일 청소도우미 자동알림"
기능과 논리적으로 충돌함을 뒤늦게 발견했다. 청소작업 레코드가
체크아웃 당일에야 생성된다면, "전날" 알림을 보낼 대상 자체가 DB에
존재하지 않아 그 기능이 물리적으로 성립할 수 없었다. 당근마켓 등
비정규 청소인력의 노쇼를 방지하려던 원래 목적과 정반대의 결과였다.

**해결**: 청소작업의 **생성 시점**과 **실제 실행 시점**을 분리했다.
예약이 `CONFIRMED` 상태로 전이되는 즉시 `scheduled_date`(체크아웃일)를
지정해 청소작업을 선제 생성하고, 실제 청소 착수는 여전히 체크아웃
당일 그대로 진행한다. 이로써 사전 알림 기능이 논리적으로 성립하게
되었고, 호스트 입장에서도 예약이 들어오는 즉시 청소 일정을 미리
확인할 수 있게 되었다.

### 9. 같은 필드를 두 문서가 정반대로 규정하고 있었음 (NOT NULL vs Optional)

**문제**: 9/4 1단계 검증에서, `INQUIRIES.reservation_id`를 DB 명세서는
`NOT NULL`로, API Contract는 "Optional(예약 전 사전문의 지원)"으로
규정하고 있는 정면 충돌을 발견했다. 더 나쁜 것은 API Contract가
**"DB도 nullable로 설계되어 있음(명세서 2.10절)"이라고 명세서를 잘못
인용**하고 있어서, 읽는 사람이 충돌 자체를 알아채기 어려웠다는 점이다.

**원인**: "예약 전 사전문의" 기능은 API 설계 단계에서 뒤늦게 추가된
요구사항인데, 그때 DB 명세서까지 되돌아가 고치지 않고 API 문서에만
반영했다. 9/5에 이 상태로 구현했다면 사전문의 INSERT가 NOT NULL 위반으로
전부 실패했을 것이다.

**해결**: 사전문의 기능을 유지하기로 결정하고 DB 쪽을 nullable로
변경했다. 이때 **PostgreSQL 복합 FK의 `MATCH SIMPLE` 동작**(구성 컬럼 중
하나라도 NULL이면 FK 검사를 통째로 스킵)을 확인해, `reservation_id`가
NULL인 사전문의 행에서는 `property_id`가 존재하지 않는 숙소여도 INSERT가
통과한다는 2차 구멍까지 발견했다. 이를 막기 위해 `property_id`에 **단독
FK를 추가로 신설**했다(단독FK = "이 숙소가 실재하는가", 복합FK = "이
예약이 정말 이 숙소의 예약인가"로 역할 분리).

### 10. 저장할 컬럼이 없는 API가 2개 존재했음

**문제**: API Contract에 `GET /channels/{id}/sync-errors`(동기화 실패
사유 조회)와 `POST /cleaning-tasks/{id}/photo`(청소 완료사진 업로드)가
정의돼 있는데, 그 데이터를 담을 컬럼이 DB 명세서 어디에도 없었다.

**원인**: API를 먼저 설계하고 스키마 반영을 나중으로 미루면서 누락됐다.
두 기능 모두 실행 체크리스트(9/13 채널연결 실패 UI, 10/3 사진업로드
VERIFIED)에 확정 작업으로 올라가 있어, 해당 날짜에 가서야 "저장할 데가
없다"는 것을 발견했을 상황이었다.

**해결**: 새 테이블을 만들지 않고 컬럼 2개만 추가했다.
`CHANNEL_CONNECTIONS.last_error_message`(TEXT, 마지막 1건만 보관하고
동기화 성공 시 NULL로 초기화)와 `CLEANING_TASKS.photo_urls`(JSONB 배열,
교체가 아니라 append 누적). 동시에 **"API Contract에 엔드포인트를 새로
적을 때는 저장할 컬럼이 명세서에 있는지 먼저 확인한다"**를 `CLAUDE.md`
규칙으로 명문화해 재발을 막았다.

### 11. 액션아이템이 다른 숙소의 예약을 참조할 수 있는 구멍

**문제**: `ACTION_ITEMS`는 `property_id`와 `reservation_id`를 각각
**서로 무관한 단독 FK**로 갖고 있었다. 그래서 "강남 숙소의 액션아이템인데
참조하는 예약은 홍대 호스텔 예약"인 행이 DB 레벨에서 아무 저항 없이
만들어질 수 있었다.

**원인**: `CLEANING_TASKS`와 `INQUIRIES`에는 계층 무결성을 위한 복합 FK를
걸어뒀으면서, 나중에 추가된 `ACTION_ITEMS`에는 같은 방어를 적용하지
않았다. 이 프로젝트의 최상위 원칙이 "Property 단위 데이터 격리"인데
정작 모든 알림이 모이는 단일 지점에 구멍이 있었던 셈이다.

**해결**: `FOREIGN KEY (reservation_id, property_id)` 복합 FK로 전환했다.
`RESERVATIONS`에 이미 `UNIQUE(reservation_id, property_id)`가 있어 추가
제약 없이 참조가 가능했다. 다만 기존 삭제 정책이 `ON DELETE SET NULL`
이었는데, 복합 FK에서 컬럼 목록 없이 `SET NULL`을 쓰면 `NOT NULL`인
`property_id`까지 NULL로 만들려다 **삭제 자체가 실패**한다는 점을 확인해,
PostgreSQL 15+의 `ON DELETE SET NULL (reservation_id)` 문법으로 명시했다.
이에 따라 로컬 Docker 이미지도 PG15 이상으로 고정하기로 했다.

### 12. 실행 지시서가 명세서 개정을 따라가지 못해 필드 2개가 빠질 뻔함

**문제**: 9/5에 그대로 복사해 실행할 `claude_code_stage1_schema.md`
지시서의 `PROPERTIES` 컬럼 목록에 `weekday_adjustment_enabled`와
`holiday_adjustment_enabled`가 없었다.

**원인**: 이 지시서는 명세서 **v1.1 시점**에 작성됐는데, v1.2에서 동적
가격조정 기능을 추가하며 위 두 필드를 명세서에만 넣고 지시서는 갱신하지
않았다. 그대로 실행했다면 필드 2개가 빠진 채 테이블이 만들어지고,

**해결**: 지시서에 두 필드와 `lower_bound_price`를 보완하고, Schema
Freeze 통과 기준에도 확인 항목으로 추가했다. 근본 원인은 "SSOT를 고칠 때
그것을 인용하는 파생 문서까지 함께 고치는 절차가 없었다"는 것이므로,
이후 3문서 기계 대조(컬럼명 diff 스크립트)를 검증 절차에 포함시켰다.
같은 검증에서 ERD 물리 스키마에 컬럼 25개가 누락돼 있던 것도 함께
발견해 보충했다.

### 13. SQLAlchemy가 PostgreSQL 15 전용 `ON DELETE SET NULL (컬럼목록)`을 렌더링하지 못함 (9/5 구현)

**문제**: 명세서 2.15절이 요구하는 `ACTION_ITEMS`의 복합FK
`ON DELETE SET NULL (reservation_id)`를 SQLAlchemy 모델에
`ondelete="SET NULL (reservation_id)"`로 그대로 적으면 테이블 생성 시점에
`CompileError: Unexpected SQL phrase`로 실패한다.

**원인**: SQLAlchemy 2.0.35는 FK의 `ondelete` 문자열을
`^(?:RESTRICT|CASCADE|SET NULL|NO ACTION|SET DEFAULT)$` 정규식으로 검증한다.
PostgreSQL 15에서 추가된 **컬럼목록을 지정하는 SET NULL 문법을 아직
지원하지 않는다.** 그렇다고 컬럼목록 없이 `SET NULL`만 쓰면, 예약 삭제 시
NOT NULL인 `property_id`까지 NULL로 만들려다 **삭제 자체가 실패**한다.

**해결**: 모델에는 표준 `SET NULL`로 선언해 DB 리플렉션과 값이 일치하도록
두고(그래야 이후 `alembic check`가 매번 차이를 보고하지 않는다), 실제 컬럼목록
문법은 두 경로 모두에 적용했다 — ① 모델 파일의 `after_create` DDL 이벤트
(`create_all` 경로), ② 초기 마이그레이션의 `op.execute` ALTER(Alembic 경로).
적용 결과는 `pg_constraint.confdelsetcols`가 `reservation_id` 컬럼만 가리키는지로
검증했고, 실제 예약 삭제 후 `reservation_id`만 NULL이 되고 행은 남는 것을 확인했다.

### 14. autogenerate가 pgvector import와 확장 생성문을 누락 (9/5 구현)

**문제**: `alembic revision --autogenerate`로 생성된 초기 마이그레이션을
그대로 `upgrade`했다면 `NameError: pgvector`와 `type "vector" does not exist`로
실패했을 것이다.

**원인**: autogenerate는 컬럼 타입을 `pgvector.sqlalchemy.vector.VECTOR(dim=384)`로
렌더링하면서도 해당 **import 문은 넣어주지 않으며**, `CREATE EXTENSION`
(`vector`, `btree_gist`)은 애초에 모델 메타데이터에 없는 정보라 생성 대상이 아니다.

**해결**: CLAUDE.md 코딩규칙 10번("생성된 파일을 바로 upgrade하지 말고 먼저
검토")대로 파일을 먼저 열어 확인하고 import 1줄과 확장 생성 2줄을 수동 추가했다.
downgrade에는 ENUM 15종 `DROP TYPE`도 함께 추가했다(테이블만 지우면 타입이 남아
재적용 시 "type already exists"로 실패). 한편 **가장 누락을 걱정했던 EXCLUDE 3종과
부분 UNIQUE 인덱스는 autogenerate가 정상적으로 잡아냈다** — 모델에
`postgresql.ExcludeConstraint`로 선언해두면 인식된다.

### 15. 지시서가 전제한 "backend 골격"이 실제로는 비어 있었음 (9/5 구현)

### 16. 비동기 테스트가 개별 실행은 통과하는데 연속 실행하면 전부 깨짐 (9/5 구현)

**문제**: 예약 무결성 회귀 테스트를 작성해 실행하니 테스트 자체는 통과하는데
(`17 passed`) 두 번째 테스트부터 **teardown에서 전부 에러**가 났다
(`sqlalchemy.exc.MissingGreenlet`). 한 개만 따로 돌리면 멀쩡히 통과해서
원인이 바로 보이지 않았다.

**원인**: 두 가지가 겹쳐 있었다.
① pytest-asyncio는 테스트마다 **새 이벤트 루프**를 만드는데, 앱의 공용 엔진
(`app/core/database.py`)은 커넥션 풀을 모듈 레벨에 들고 있다. 첫 테스트의
루프에 묶인 asyncpg 커넥션을 다음 테스트가 재사용하는 순간 깨진다.
② 정리(teardown) 코드에서 `await session.rollback()` 뒤에 `obj.host_id`를
읽었는데, rollback은 인스턴스 속성을 만료시키므로 이 접근이 **지연로딩(동기
IO)** 을 유발한다. async 컨텍스트에서 동기 IO를 하면 같은 예외가 난다.

**해결**: ① 테스트 세션은 `NullPool` 엔진으로 따로 만들어 커넥션을 재사용하지
않게 했고, ② PK를 rollback 전에 값으로 미리 뽑아두도록 고쳤다. 이후 18개
테스트가 연속 실행에서 전부 통과한다. **앞으로 추가할 비동기 테스트도 앱
공용 엔진을 그대로 쓰지 말 것** — 같은 증상이 반복된다.

### 17. 로컬 Postgres와 Supabase의 메이저 버전이 갈라져 있었음 (9/5)

**문제**: 9/5 스키마 구현 시 로컬 Docker 이미지를 `pgvector/pgvector:pg16`
으로 잡았는데, 이후 프로덕션 Supabase가 **PostgreSQL 17.6**임이 확인됐다
(Gemini 교차검증 완료). 로컬 16 / 운영 17로 메이저 버전이 갈라진 상태였다.

**원인**: 명세서 5절의 요구사항을 "15 이상이면 된다"로만 읽었기 때문이다.
그 조항의 실제 취지는 두 가지인데, 앞의 하나만 충족한 상태였다 —
① `ON DELETE SET NULL (컬럼목록)`이 PG15+ 전용이라 최소 15가 필요하다,
② **로컬 Docker와 Supabase를 같은 메이저로 맞춘다(dev/prod parity)**.
메이저가 다르면 예약 겹침방지에 쓰는 `EXCLUDE ... USING gist`, `tsrange`,
부분 UNIQUE 인덱스, pgvector 같은 요소가 로컬에서만 통과하고 배포에서
달라져도 발표 직전까지 모른 채 지나갈 수 있다.

**해결**: `docker-compose.yml` 이미지를 `pg17`로 올리고, 이미지만 바꾸는
데서 끝내지 않고 **빈 DB에서 스키마 전체를 다시 만들어** 재현되는지까지
확인했다(`docker compose down -v` → `alembic upgrade head`). PG17.11에서
16개 테이블 / ENUM 15종 / EXCLUDE 3종 / `confdelsetcols`(컬럼목록 SET NULL)
/ 확장 2종이 모두 그대로 생성됐고, 회귀 테스트 20개(예약 무결성 18 +
헬스체크 2)와 `alembic check`도 전부 통과했다. 마이그레이션 수정은
필요 없었다 — 즉 이번 건은 실제 장애가 아니라 **터지기 전에 막은 시한폭탄**
이었다.

**교훈**: 버전 제약을 "최소 몇 이상"으로만 기억하면 parity 요구를 놓친다.
로컬/운영 버전은 숫자를 직접 뽑아 **대조**해야 하고, 버전을 바꾼 뒤에는
반드시 빈 DB에서 마이그레이션을 다시 돌려봐야 한다.

### 18. 배포 3주 전에 미리 확인한 Supabase 확장 설치 권한 (9/5, 사전확인 성공)

**문제(잠재)**: 우리 스키마는 PostgreSQL 확장 2개에 의존한다 —
예약 겹침방지 `EXCLUDE ... USING gist`에 필요한 `btree_gist`,
`KNOWLEDGE_CHUNKS.embedding VECTOR(384)`에 필요한 `vector`(pgvector).
관리형 서비스는 보안상 `CREATE EXTENSION`을 제한하는 경우가 있어, 이게
막히면 **초기 마이그레이션이 첫 줄에서 실패**한다. 10/1 배포 당일에
처음 시도했다면 대응할 시간이 없었을 지점이다.

**원인(확인 필요했던 이유)**: CLAUDE.md 코딩규칙 10번은 "프로덕션(Supabase)
반영은 앱 배포 전에 미리 적용"을 요구한다. 그런데 로컬에서 잘 되는 것은
근거가 되지 못한다 — 로컬 Docker는 superuser로 붙지만 관리형 DB는 권한이
축소된 롤로 붙기 때문이다.

**확인 결과(성공)**: 9/5에 Supabase 대시보드에서 직접 확인했다.
- `vector` **0.8.2**, `btree_gist` **1.7** 둘 다 Enable 성공. 권한 오류
  (`42501 permission denied to create extension`) 없음.
- 설치 스키마는 `public`이 아니라 **`extensions`**.
- `SELECT '[1,2,3]'::vector` → `[1,2,3]` 정상 반환. 즉 `extensions` 스키마에
  설치됐음에도 `search_path`에서 타입이 정상적으로 해석된다.
- 이번 확인은 **확장 권한만** 대상으로 했고 테이블은 만들지 않았다
  (전체 마이그레이션은 10/1에 정식 진행).

**남은 확인 1건(10/1 체크포인트)**: 위 `::vector` 검증은 대시보드 SQL
Editor 세션에서 이뤄졌다. `search_path`는 **롤/세션마다 다를 수 있으므로**,
애플리케이션이 붙는 접속(alembic/asyncpg)에서도 동일한지는 10/1에
마이그레이션을 돌릴 때 확인한다. 만약 그 세션에서 타입을 못 찾으면
(`type "vector" does not exist`) 해결책은 둘 중 하나다 —
`alembic/env.py`에서 접속 직후 `SET search_path TO public, extensions`를
실행하거나, 마이그레이션의 컬럼 타입을 `extensions.vector(384)`로
스키마 한정한다. **로컬(pgvector 0.8.6, public 스키마)과 Supabase(0.8.2,
extensions 스키마)의 이 차이는 정상이며 문제가 아니다.**

**교훈**: 배포 리스크는 "배포 때 해보면 안다"가 아니라, **가장 먼저
실패할 한 줄을 미리 골라 그것만 따로 확인**하면 대부분 3주 전에 끝난다.
이번 확인에 든 시간은 5분이었다.

### 20. 체크리스트 포인트/주의 문구가 태스크와 어긋난 사례 발견 (9/6, 미조치)

**문제**: 체크리스트 엑셀의 "가장 중요한 포인트 / 주의할 점" 문구가
태스크 내용과 맞지 않는 경우가 있다. 9/6에 E2E 리허설(10/11) 행에서

### 21. 전수 재검증에서 스키마는 정적 대조로만 확인됐고 Docker 기동에 실패 (9/6~9/7)

**문제**: 9/6 밤 8/31~9/6 전체 작업을 전수 재검증하면서 DB 실물 확인
(`\dt` 16개 테이블, `\dx` vector·btree_gist, EXCLUDE 3종이 실제 DB에
걸려 있는지, `alembic check` 드리프트)을 시도했으나 **Docker 엔진이
기동되지 않아 전부 확인하지 못했다.** 회귀테스트도 20개 중 2개
(`test_health.py`)만 실행됐고, `test_reservation_integrity.py` 18개는

**원인**: Docker Desktop을 기동했으나 로그에
`[Docker Desktop.exe] backend process exited`가 남고 이후

### 22. CHECKLIST_ITEMS 생성 시점 미정의 발견 (9/7)

**문제**: UI 설계 중 `/compliance` 화면의 빈 상태를 정의하려다,
`CHECKLIST_ITEMS` 데이터가 언제 생성되는지 어느 문서에도 정의돼

그 파생을 수행하는 주체와 시점이 설계되지 않은 채 컬럼만 먼저
정의됐다. CLAUDE.md의 "정적 체크리스트 템플릿 + 만료알림 수준"이라는

**해결**: UI 빈 상태 설계를 확정하지 않고 미정으로 표시했다

**9/8 추가 — 화면 배치를 바꾸면서 해소됨**: 강사님 피드백("화면이
정말 필요한지부터 검토하라")에 따라 재검토한 결과, `/compliance`
전용 화면을 `/settings` 4번째 탭으로 흡수했다(세 차례 독립 검토
일치, 라우트 12→11 / 사이드바 9→8). **설정 화면에서 호스트가 직접
항목을 추가하는 구조**가 되므로 생성 경로 문제가 함께 풀린다 —
전용 조회 화면에서는 어색했던 "호스트가 직접 만든다"가 설정
화면에서는 자연스럽다. **수동 생성으로 확정**하고 빈 상태도
`+ 항목 추가` CTA로 확정했다(`docs/ui_design.md` 4-11절 탭 4).
`POST` 엔드포인트의 **요청 스펙 확정은 컴플라이언스 구현 시점
(10/1~07)에 한다** — 생성 주체가 정해진 것과 요청 바디가 정의된
것은 다르다.

> 기능·데이터·API·만료 알림은 전부 그대로다. 바뀐 것은 조회
> 위치뿐이며 기능 축소가 아니다.

**교훈**: 컬럼이 `NOT NULL`로 존재한다는 것이 그 값을 채우는 경로가

### 23. API 응답 스펙 미정의 엔드포인트 7개 발견 (9/7)

**문제**: R35 와이어프레임 작성 중, 화면 요소의 데이터 출처를
적으려 했으나 `api_contract.md`에 응답 스펙(응답 예시·필드 정의)이
아예 없는 엔드포인트가 7개 발견됐다.

- `settlements` (5절)
- `financial-config` (5절)
- `action-items` (9절) — ✅ **해소: v2.0(9/8)**
- `inquiries` 목록 (7절)
- `knowledge-chunks` (8절)
- `channels` (3절) — ✅ **해소: v2.1(9/8)**
- `rooms` / `beds` (2절) — ✅ **해소: v2.1(9/8)**

> **해소 현황(9/8 기준): 7건 중 3건 해소, 남은 것 4건**
> — `settlements` / `financial-config` / `inquiries` 목록 /
> `knowledge-chunks`.
>
> 위 목록의 7건은 **성격이 전부 같다** — 테이블은 실재하고 API 응답
> 예시만 없는 누락이다. `financial-config`도 예외가 아니다:
> `FINANCIAL_CONFIGS`는 DB명세서 2.7절과 마이그레이션에 이미 존재하며
> (`config_id`·`commission_rate`·`base_nightly_rate` 등 7컬럼),
> 응답 스펙만 없다. 10/2 정산 구현 착수 전에 확정한다.
>
> **테이블 자체가 없는 것은 이 목록에 없다.** 그런 항목은 `/checkin`
> (비대면 체크인)이며, api_contract 엔드포인트 0개·DB 도메인 부재로
> 9/29~30에 데이터 설계부터 시작한다(`docs/ui_design.md` 3절).
> 두 가지는 필요한 작업이 다르므로 섞지 않는다.

같은 날 오전에 `dashboard/summary`와 `GET /properties` 두 건의
응답 스펙을 확정(v1.8)했는데, 같은 성격의 누락이 7건 더 남아
있었다.

**원인**: api_contract는 엔드포인트 목록(Method/Endpoint/설명)을
표로 정리하는 형식이고, 응답 예시는 일부 핵심 엔드포인트에만
붙어 있다. 표에 한 줄 있으면 "정의됐다"고 간주하기 쉬워, 응답
구조가 비어 있다는 사실이 드러나지 않았다.

**해결**: 와이어프레임에서 필드명을 지어내지 않고, 출처를 두 가지로
구분해 표기했다(`docs/ui_wireframe.md`).
- 필드명 그대로 = api_contract v1.8에 응답 예시가 있는 확정 필드
- `[DB]` 접두 = API 응답 스펙이 없어 DB명세서 v1.3 컬럼명을 적은 것

각 화면 구현 시점에 해당 엔드포인트의 응답 스펙을 api_contract에
먼저 확정한 뒤 프론트를 작성한다. 특히 정산(10/2~06)과
액션센터(10/6)는 마감 직전이라 그 시점에 발견하면 위험하므로,
착수 전 응답 스펙 확정을 선행 작업으로 잡는다.

**부수 발견**: AI 인박스의 "재생성 잔여 횟수"는 api_contract 7절에
계산식(`INQUIRY_RESPONSES 레코드수 - 1`, 상한 2)만 있고 이를 담을
응답 필드가 없다. 프론트가 직접 세면 서버의 429 판정과 어긋날 수
있으므로 서버가 내려주는 쪽이 맞으나, 확정은 AI 응대 구현
시점(9/17~28)으로 미룬다.

**교훈**: 엔드포인트 표에 한 줄 있다는 것이 응답 구조가 정의됐다는
뜻은 아니다. 22번(`NOT NULL` 컬럼은 있는데 채우는 경로가 없음)과
같은 계열 — 껍데기는 있고 내용이 없는 누락이다. 화면 설계나 프론트
구현 착수 전에 "이 엔드포인트에 응답 예시가 있는가"를 먼저 확인한다.

### 24. ACTION_ITEMS 미정의 3건 — resolved_at 부재, 가격추천 필드 저장위치, AUTO_RESOLVED 로직 (9/7)

**문제**: action-items 응답 스펙을 확정하는 과정에서 세 가지가 문서에
정의돼 있지 않음을 발견했다.

**(1) `resolved_at` 컬럼 부재 — 기능 결손**

`ACTION_ITEMS`에 `created_at`만 있고 `resolved_at`이 없다. `/actions`
화면의 "처리 이력"을 처리 시각순으로 정렬할 수 없다. `created_at`으로
대체가 불가능하다: 3개월 전 생성된 서류 만료 알림을 어제 처리했다면,
`created_at` 정렬에서 그 항목은 목록 맨 아래에 묻힌다. **"최근에 무엇을
처리했나"라는 질문에 답할 데이터 자체가 없다.** 정렬 방식의 문제가 아니라
존재하지 않는 데이터를 요구하는 질문이다.

**(2) `price-recommendations` 응답 7필드의 저장 위치**

api_contract 13절의 `GET /properties/{id}/price-recommendations` 응답에
`date`, `day_type`, `current_price`, `recommended_price`, `delta`,
`reason`, `below_lower_bound` 7개 필드가 있으나 `ACTION_ITEMS`에 해당
컬럼이 없다. `content`(TEXT)에 구조화 데이터로 넣는지, 서버가 매번
계산하는 파생값인지 정의가 없다.

**(3) `AUTO_RESOLVED` 세팅 주체**

ENUM 정의(명세서)와 ERD 표기에만 등장하며, 언제 누가 이 값을 넣는지
설명이 없다. `risk_level='GREEN_AUTO'`와의 관계도 미정이다.

**원인**: 13절은 9/4에 "명세서 6절에 기능은 있는데 대응 API가 없다"는
누락을 메우며 추가됐다. 그때 응답 필드는 화면 요구에서 도출했으나 저장
위치를 함께 확인하지 않았다. `resolved_at`과 `AUTO_RESOLVED`는 상태 전이
로직이 아직 설계되지 않아 함께 누락됐다.

**해결**: 세 건 모두 확정하지 않고 기록했다. 스키마는 검증이 끝난
상태이므로 안정성 우선 원칙에 따라 지금 건드리지 않는다.

- **(1)** 1차에서는 "처리 시각순 처리 이력"을 제공하지 않는다. `RESOLVED`
  목록은 `created_at DESC`로 대체 표시하며, 이 한계를 api_contract에
  명시했다(9.1절). **`resolved_at` 컬럼 추가는 다음 스키마 변경 라운드의
  필수 반영 항목으로 확정한다.** 액션센터 구현 시점(10/6)에 resolve
  로직과 함께 처리한다.
- **(2)** 동적 가격 조정 구현 시점(10/5~07)에 정한다.
- **(3)** 액션센터 구현 시점(10/6)에 트리거 규칙과 함께 정한다. 그
  전까지 `GREEN_AUTO` 항목의 실질적 자동 해결은 동작하지 않는다.

**교훈**: 22번(`NOT NULL` 컬럼은 있는데 채우는 경로가 없음),
23번(엔드포인트는 있는데 응답 스펙이 없음)에 이어 **세 번째 계열**이다 —
응답 필드는 정의됐는데 저장 컬럼이 없고, 상태값은 선언됐는데 전이 로직이
없다. API 스펙을 적을 때 **"이 필드가 어느 컬럼에서 오는가"**, ENUM을
선언할 때 **"이 값을 누가 언제 넣는가"**를 값 단위로 확인해야 한다.

### 25. Vite react-ts 템플릿에 strict가 없음 (9/8)

**문제**: 프론트엔드 첫 세팅에서 Vite react-ts 템플릿의
`tsconfig.app.json`에 **`strict`도 `strictNullChecks`도 아예 없었다.**
`noUnusedLocals` 같은 린팅 옵션만 있었다.

**원인**: 템플릿 기본값이 그렇다. "TypeScript 템플릿이니 strict는 켜져
있겠지"라는 가정이 틀렸다.

**해결**: 세팅 직후 `"strict": true`를 추가하고, `conflict_count`가
nullable이라 필요하다는 이유를 주석으로 남겼다.

**교훈**: 이걸 못 잡았으면 api_contract v2.0의
`conflict_count: number | null`을 타입에 정의해놓고도 **컴파일러가 `number`와
`number | null`을 구분하지 않아**, null 체크를 빼먹은 채로 배포까지 갔을
것이다. **템플릿이 제공하는 설정을 확인 없이 신뢰하지 않는다.** 새 도구를
도입할 때 기본값을 한 번 열어본다.

### 26. StrictMode 이중 마운트와 cancelled 플래그 충돌 (9/8)

**문제**: 대시보드가 로딩 상태에서 멈춰 데이터가 표시되지 않았다. API
호출은 성공하는데 화면이 갱신되지 않았다.

**원인**: React StrictMode가 개발 모드에서 effect를 **마운트 → cleanup →
재마운트**로 두 번 실행한다. 훅에 중복 방지 ref 가드와 cleanup의
`cancelled = true` 플래그가 함께 있었는데:

1. 첫 실행이 시작되고 fetch가 진행 중
2. cleanup이 돌아 `cancelled = true`
3. 두 번째 실행은 ref 가드에 막혀 아무것도 하지 않음
4. 첫 실행의 응답이 도착했으나 `cancelled` 때문에 **전부 버려짐**

**해결**: `cancelled` 플래그를 제거했다. 중복 실행 방지는 ref 가드 하나로
충분하며, **두 장치를 함께 쓰면 서로를 무력화한다.** 재발 방지 주석을 훅에
남겼다.

**교훈**: 앞으로 화면 11개를 더 만들며 같은 훅 패턴을 반복해서 쓴다.
**데이터 페칭 훅에서 중복 방지와 취소를 동시에 넣지 않는다.** StrictMode는
프로덕션 빌드에서 한 번만 실행되므로 **개발에서만 재현되는 종류의 버그**다.
개발에서 안 되는데 빌드하면 되는 상황이 오면 이 패턴을 먼저 의심한다.

※ 같은 계열의 다른 사례는 **28번** 참고(setState 업데이터 내 부작용).

### 27. openapi-typescript peer 의존성 충돌 (9/8)

**문제**: 프론트엔드 세팅에서 openapi-typescript 7.13.0이
`typescript ^5.x`를 peer 의존성으로 요구하는데, Vite react-ts 템플릿이
설치하는 것은 **TypeScript 6.0.3**이라 설치가 거부됐다(`ERESOLVE`).

**원인**: openapi-typescript의 peer 범위가 아직 TS 6을 반영하지 못한
것으로 보인다. 도구 쪽 대응이 늦은 경우다.

**해결**: `--legacy-peer-deps`로 설치했다. **실제 실행은 정상**이며
`npm run generate-api`로 `/openapi.json`에서 타입 생성이 성공했다.

TS를 5.x로 내리는 대안은 채택하지 않았다. 템플릿 기본값을 거스르는 쪽이
위험이 크고, 실행에 문제가 없기 때문이다.

**함께 발견된 것**: TS 6에서 `baseUrl`이 deprecated되어 tsconfig에서
제거하고 `paths`만 남겼다. tsconfig 기준 상대경로로 동작한다.

**교훈**: `npm ci`나 CI 환경에서 같은 충돌이 재현된다. 그때 원인을 다시
파헤치지 않도록 이 기록을 남긴다. **배포 파이프라인을 구성할 때(10/1)
같은 플래그가 필요한지 확인할 것.** openapi-typescript가 TS 6을 지원하면
플래그를 뺀다.

### 28. StrictMode 이중 호출과 상태 갱신 함수 내 부작용 (9/8)

**문제**: 대시보드 PARTIAL 상태에서 개별 숙소 재시도 버튼을 눌러도 아무
반응이 없었다. **요청 자체가 나가지 않았다.**

**원인**: setState 업데이터 안에서 외부 변수를 바꿨다.

```ts
let shouldFetch = true;
setFetchMap((prev) => {
  if (current?.status === "loading") { shouldFetch = false; return prev; }
  ...
});
if (shouldFetch) void loadSummary(propertyId);
```

React StrictMode는 개발 모드에서 **상태 갱신 함수도 두 번 호출**한다.
첫 호출이 상태를 `loading`으로 바꾸고, 두 번째 호출이 이미 `loading`인
상태를 보고 `shouldFetch = false`로 뒤집어 실제 요청이 나가지 않았다.

**업데이터는 순수 함수여야 하는데 부작용이 들어간 것**이 근본 원인이다.

**해결**: `fetchMapRef`(최신 상태 거울)를 두고 **업데이터 바깥에서** 가드를
판정하도록 바꿨다. 업데이터는 순수 함수로 유지된다.

**26번과의 관계**: 같은 계열이지만 위치와 증상이 다르다.

| | 위치 | 증상 |
|---|---|---|
| **26번** | `useEffect` + cleanup의 `cancelled` 플래그 | 요청은 나갔으나 **응답이 버려짐** |
| **28번** | setState 업데이터 내 외부 변수 변경 | **요청이 아예 안 나감** |

**교훈**: 앞으로 화면 11개에서 같은 데이터 페칭 패턴을 반복한다.
StrictMode 관련 문제를 이번 프로젝트에서 **두 번** 겪었으므로 규칙으로
굳힌다.

- **setState 업데이터 안에서 외부 변수를 읽거나 쓰지 않는다.** 판정이
  필요하면 ref로 최신 상태를 따로 두고 **업데이터 바깥에서** 한다.
- **useEffect의 중복 방지와 취소를 동시에 넣지 않는다**(26번).
- 개발에서만 재현되고 프로덕션 빌드에서는 안 나는 종류다. **"개발에서
  이상한데 빌드하면 되는" 상황이면 이 패턴을 먼저 의심한다.**

### 29. openpyxl 조건부서식 제자리 수정 중 파일 손상 (9/9)

**문제**: 체크리스트 엑셀에 태스크 3건을 신설하면서 조건부서식 범위를
`E4:E128` → `E4:E131`로 확장하려 했다. `sqref`를 제자리에서 수정한 뒤
저장하자 **저장이 중단되고 원본이 91,206바이트에서 9,332바이트로
손상**됐다. 다시 열 수 없는 상태였다(`[Content_Types].xml` 부재).

```python
# 이렇게 했다 — 저장 시 KeyError
for rng, rules in ws.conditional_formatting._cf_rules.items():
    rng.sqref = MultiCellRange(str(rng.sqref).replace("128", "131"))
```

**원인**: openpyxl에서 `ConditionalFormatting` 객체는 **자기 자신이
내부 딕셔너리(`_cf_rules`)의 키**다. `sqref`를 바꾸면 객체의 해시가
달라져 **자신이 들어 있던 딕셔너리에서 자기를 찾을 수 없게 된다.**
저장 단계에서 규칙을 순회하다 `KeyError`가 나고, 그 시점까지 쓴
부분만 남은 채 파일 쓰기가 끊긴다. 문자열처럼 보이지만 제자리 수정이
안전하지 않은 값이다.

**해결**: 작업 전 떠둔 타임스탬프 백업에서 복원하고 MD5로 원본과
일치함을 확인했다. 이후 **스크래치패드 사본에서 작업 → 검증 통과 →
원본에 반영** 순서로 바꿨다.

**올바른 방법**: 기존 규칙 객체를 수정하지 말고, **목록을 새로 만들어
확장된 범위로 다시 등록**한다.

```python
from openpyxl.formatting.formatting import ConditionalFormattingList
newcf = ConditionalFormattingList()
for cfobj in ws.conditional_formatting:          # 공개 API로 순회
    sq = str(cfobj.sqref).replace("128", "131")
    for rule in cfobj.rules:
        newcf.add(sq, rule)                      # 새 범위로 재등록
ws.conditional_formatting = newcf
```

> 데이터유효성(`ws.data_validations.dataValidation`)은 **리스트**라
> `dv.sqref` 제자리 수정이 안전하다. 같은 "범위 확장"이라도 자료구조가
> 달라 방법이 갈린다. **openpyxl의 `_`로 시작하는 내부 객체나 딕셔너리를
> 직접 변형하지 않는다.**

**교훈 — 검증 항목이 손상을 못 잡았다**: 8-2 절차의 무결성 검증 6항목
(차트·이미지·피벗 0 / 조건부서식 2 / 데이터유효성 4 / 수식 61)은
**빈 파일에서도 전부 통과한다.** 차트·이미지·피벗은 "0개"가 정상값이고,
나머지 셋은 시트가 비면 세어지지 않아 검증 자체가 성립하지 않는다.
**91,206 → 9,332바이트라는 가장 명백한 신호를 보는 항목이 없었다.**

9/9자로 8-2를 보강했다.
- **작업 전 백업**(타임스탬프, 저장소 밖) + **사본 작업 후 원본 반영**.
  엑셀은 바이너리라 `git diff`로 손상을 알 수 없어 백업이 유일한 복구
  수단이다.
- **5단계 검증**: 파일 크기 → 재오픈 → 시트 → 구조 → 내용. 앞 단계가
  실패하면 뒤를 진행하지 않는다. 다만 **크기만으로 정상을 단정하지
  않는다** — 압축률에 따라 정상 범위에서도 변하므로 나머지 4단계가
  함께 필요하다.

차단**되었다. 이는 구현 이후 발견했다면 훨씬 큰 재작업 비용이 들었을
문제들이며, 개발자가 AI 도구를 활용하면서도 설계 기준과 최종
의사결정을 주도적으로 수행했음을 보여준다.

**13~17번의 성격**: 반대로 이 5건은 설계가 아니라 **구현 도구의 한계와
실행 환경**에서
나왔다. 명세서가 요구한 PostgreSQL 15 문법을 ORM이 지원하지 않거나
(13번), 자동생성 도구가 일부 DDL을 빠뜨리는(14번) 경우로, 문서 대조로는
미리 잡을 수 없고 실제로 실행해봐야 드러난다. "자동생성 결과를 바로
적용하지 말고 먼저 검토한다"는 규칙이 실제로 사고를 막아준 사례다.
16번은 한 걸음 더 나아가, **테스트를 하나씩 돌리면 안 보이고 전부 돌려야
보이는 종류의 결함**도 있다는 것을 보여준다. 17번은 코드가 아니라
**실행 환경(로컬 DB 버전)이 운영과 어긋나 있던 경우**로, 문서의 버전
제약을 최솟값으로만 읽으면 놓치게 되는 유형이다.

**9~12번에서 얻은 교훈**: 문서가 늘어나면 "각 문서는 맞는데 서로
어긋나는" 오류가 생기고, 이것은 사람이 눈으로 읽어서는 잘 안 보인다.
그래서 1단계 검증에서는 **명세서의 `CREATE TABLE` 블록과 ERD의 엔티티
정의를 파싱해 컬럼명을 기계적으로 diff**하는 방식을 썼고, 그 결과
사람이 5번 읽어도 못 찾았던 누락 25건을 한 번에 찾아냈다. 이후 단계
검증에도 같은 방식을 적용한다.

### a) 9/5 CLAUDE.md 덮어쓰기 사고 규명 — 오늘의 최대 발견

CLAUDE.md에 9/4 확정사항 6건이 없는 것을 발견하고 git 이력으로 원인을
규명했다.

```
9/4 15:13  36dbec9  retry_count >= 2 도입
9/4 16:14  c34f83a  scheduled_at 개명 반영
9/5 12:24  3bcedc3  둘 다 소실   CLAUDE.md | 27 +, 36 -
```

`3bcedc3`은 커밋 메시지가 "AI역할분담 원칙 추가"인데 실제 diff는
**27줄 추가 36줄 삭제**였다. 정상적인 섹션 추가의 모양이 아니라, 9/4
정정 이전 버전을 기준으로 만든 전문이 통째로 커밋된 것으로 보인다.

**오염 범위를 전수 확인한 결과 CLAUDE.md 단독이었다.** DB명세서·
api_contract·state_events·troubleshooting은 전부 정상이었고, 모델 3종과
마이그레이션이 명세서와 100% 일치했다. **문서보다 강한 증거인 구현
코드가 명세서를 뒷받침했다.**

**결정적 증거 두 가지**

1. 커밋 메시지("추가")와 실제 diff(36줄 삭제)의 **불일치**가 원인 규명의
   단서였다.
2. `troubleshooting.md` 135행이 *"…를 `CLAUDE.md`에 추가했다"*고
   기록하고 있었다. **기록은 남았는데 실물이 사라진 상태**였다.

**복구 결과** — 614행 → 645행. 추가 35줄, 삭제 4줄. 삭제 4줄은 전부
**틀린 값이 올바른 값으로 교체된 것**이다(`count>=3` → `retry_count >= 2`,
`scheduled_date=check_out` → `scheduled_at = check_out + checkout_time`,

규칙은 세웠지만 **그 사고가 이미 남긴 피해는 복구되지 않은 채 나흘간
남아 있었다.** 재발 방지 규칙을 만들 때는 그 규칙을 촉발한 사고의 기존
피해를 함께 복구했는지 반드시 확인해야 한다. 규칙 신설로 사고가
"처리됐다"고 느끼는 것이 함정이다.

**부수 확인**: 8-1 신설 이후 **22개 커밋 동안 재발 없음**. 규칙 자체는
작동하고 있다. 문제는 규칙의 실효성이 아니라 **소급 복구가 빠진 것**이었다.

  원본 반영**. 엑셀은 바이너리라 `git diff`로 손상을 알 수 없다
- **4번을 5단계로 교체** — 파일 크기 → 재오픈 → 시트 → 구조 → 내용.

논의**였다. 이미 결정된 사실을 다시 논의하는 경우를 커버하지 못한다.

> **크로스체크 권고**: *"새로운 주제를 논의하기 전, 관련 troubleshooting·

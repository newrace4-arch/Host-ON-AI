### 1. 프로젝트 주제 및 핵심 개요

**🎯 프로젝트 핵심 정의 (Core Statement)**

외국인관광 도시민박업(3룸 독채 통대여)과 호스텔(객실/도미토리 침대 판매)을 동시에 운영하는 1인 멀티호스트가 겪는 야간 다국어 응대, 더블부킹, 청소 누락, 2026년 플랫폼 단일 수수료(15.5%) 정산 왜곡을 단일 시스템으로 해결하는 AI Agent 기반 운영 자동화 SaaS

#### 가. 추진 배경 및 실무적 Pain Points

공유 숙박 생태계 확대로 1인이 복수 숙소를 운영하는 멀티호스트가 급증했으나, 기존 호텔용 PMS는 독채 통대여와 객실/침대 분할 판매를 동시에 제어하지 못합니다. 또한 시차를 가리지 않는 외국인 게스트의 24시간 응대 피로, OTA 채널 간 iCal 동기화 시점 충돌로 인한 중복 예약, 체크아웃 직후 짧은 턴어라운드 시간(11시~15시) 내 청소 배정 지연, 2026년 5월 25일부터 시행된 에어비앤비 국내 단일 수수료 정책(15.5%) 미반영으로 인한 수기 엑셀 정산의 한계가 심각합니다.

#### 나. 벤치마킹 분석 및 차별화 전략

국내 PMS 1위(온다), 글로벌 1인 호스트 SaaS 표준(Hospitable)을 비교 분석하고, 해외 엔터프라이즈형 서비스(Guesty)의 판매단위별 과금 구조 사례를 참고하여 틈새 시장의 명확한 차별성을 확보했습니다.

| 비교 기준 | 온다 (ONDA) [국내 1위] | Hospitable [글로벌] | Host ON (AI) [본 프로젝트] |
| --- | --- | --- | --- |
| **타깃 / 운영모델** | 중소 호텔·대형 펜션 (위탁수수료형) | 1~3개 에어비앤비 개인 호스트 | **국내 1인 복합 멀티호스트 (완전 독립형)** |
| **공간 계층 수용** | 단일 객실 타입 중심 (호텔형) | 단일 리스팅 1:1 매핑 | **Host-Property-Room-Bed 복합 계층** |
| **AI 고객 응대** | 정형 챗봇 또는 관리자 수동 대응 | 정형 룰/템플릿 기반 자동 발송 | **숙소 격리 RAG + Claude 단일호출 + 승인 루프** |
| **가격 및 정산** | 거래 연동 수수료, 실시간 조인 | 달러 단순 매출 집계 | **공백일 미세조정 + 2026 단일요율 불변 스냅샷** |
| **국내 컴플라이언스** | 대형 숙박업 규격 중심 | 국내 법령/서식 대응 불가 | **'외국인관광 도시민박업' 법정 서식 및 D-30 신고** |

**💡 실증적 시장 결핍 사례 (제주도 사장님 자체제작 무료 PMS)**

"에어비앤비, 아고다 연동 수수료와 월 이용료가 과하여 직접 CMS를 만들었다"는 실제 호스트 사례처럼, 1인 멀티호스트의 운영 결핍은 실재하며 Host ON (AI)은 이를 완벽히 해결하는 솔루션입니다.

### 2. 사전 크로스체크를 통한 아키텍처 검증 이력 (6차례)

본 프로젝트는 개발 착수 전 데이터 무결성과 비즈니스 로직을 검증하기 위해 총 6차례의 엄밀한 엔지니어링 크로스체크를 수행하여 리스크를 선제 제거했습니다.

| 검증 차수 | 초기 기획 및 발견된 결함 | 크로스체크 검증 및 해결 방식 | 아키텍처 확정 결과 |
| --- | --- | --- | --- |
| **1차 검증** | 한 숙소에 복수 숙박업 등록 가정 | 관광진흥법 시행령상 동일 공간 복수 등록 불가 확인 | `accommodation_type` 단일 ENUM |
| **2차 검증** | DB CHECK로 숙소유형 교차검증 시도 | PostgreSQL 일반 CHECK는 타 테이블 조회 불가 한계 인지 | DB(형식제약)와 App(비즈니스검증) 분리 |
| **3차 검증** | 문의 응대 1:1 단순 매핑 설계 | 재시도 및 호스트 수정 시 과거 이력 유실 결함 발견 | 1:N 이력 보존 + `is_latest` 부분인덱스 |
| **4차 검증** | 정산서-수수료설정 FK 직접 연결 | 수수료율 인상 시 과거 모든 월의 정산서 소급 변조 위험 | FK 제거 후 `applied_rate` 스냅샷 불변화 |
| **5차 검증** | 에어비앤비 수수료 3.3% 가정 | 2026.5.25 국내 단일 수수료 정책(15.5%) 전환 확인 | 기본 요율 0.155로 전면 정정 |
| **6차 검증**(09/02 신규) | 주중 공백일 방치 및 성수기 누락 | 3박 연박 설정으로 인한 평일 공백 및 성수기 미조정 손실 | 신규 공백일 자동조정 + 방치감지 탑재 |

#### 나. 1차 MVP 구현 범위 및 2차 로드맵 경계

**1차 확정 범위 (~10/10 제출) 핵심 운영 자동화 풀스택 완성**
- 공간/예약: Host-Property-Room-Bed 계층, 독채 예약 시 하위 Room 전체 잠금 인터셉터, 상태 3종 독립 분리
- AI Agent: 숙소별 지식 격리 RAG, Claude 1회 통합 호출, 규칙 기반 위험도 판정, 재시도 상한(최대 총 3회)
- 운영 관리: iCal 다채널 동기화 충돌 감지, 예약확정 연동 청소 선제발행, 비대면 체크인 Mock, Action Center 3단계 큐
- 가격/정산: 공백일 자동 미세조정(신규), 성수기 방치 감지, 2026 단일 수수료율(0.155) 불변 스냅샷 정산

**2차 로드맵 (MVP 범위 제외)**: 실제 스마트락 하드웨어 제어, 외부 경쟁사 크롤링 동적 가격, 채널당 다중 연결, 부가세 계산서 발행

### 3. 시스템 구조 플로우차트 및 데이터 모델 (ERD)

#### 가. 시스템 구조 플로우차트 (End-to-End Architecture)

운영 라이프사이클과 AI Agent 문의응대 파이프라인이 `RESERVATIONS` 엔티티를 매개로 유기적으로 결합된 2-Tier 구조입니다.

**[서브그래프 1: 핵심 운영 라이프사이클]**
iCal 피드 동기화(OTA 예약 인입 감지) ➔ 충돌 감지 & 검증(중복 시 🔴 긴급알림) ➔ RESERVATIONS(예약/환불/정산 저장) ➔ 청소 및 정산 연결(1:1 청소 / 월정산 스냅샷)

**[서브그래프 2: AI Agent 문의응대 & 루프백 제어]**
게스트 문의(INQUIRIES 저장) ➔ 컨텍스트 바인딩(property_id 격리 RAG) ➔ Claude 단일 통합호출(분류·위험도·다국어·근거) ➔ 규칙엔진 경로 판정(LOW(자동) / 고위험(승인))
※ 승인 거절 시: [재시도 횟수 ≤ 2회(최초 포함 총 3회)?] 분기 ➔ 초과 시 호스트 수동 모달 폴백으로 무한 루프 완벽 차단.

#### 나. 핵심 논리적 데이터베이스 스키마 (Core ERD 구조)

| 테이블명 | 주요 식별자 및 속성 | 데이터 무결성 제약조건 및 핵심 설계 원칙 |
| --- | --- | --- |
| PROPERTIES(숙소) | property_id (PK), name, accommodation_type, checkin_time, **weekday_adjustment_enabled**, **holiday_adjustment_enabled** | 단일 ENUM(관광진흥법 시행령상 1공간 1유형), v1.2 신규 **평일자동조정 / 연휴자동조정** 불리언 필드 탑재 (공백일 미세조정 SSOT) |
| **ROOMS / BEDS** | room_id, bed_id, property_id | Host-Property-Room-Bed 계층형 구조 (독채 운영 시 모두 Optional 허용) |
| **RESERVATIONS** | reservation_id (PK), property_id, status 3종 | (channel_connection_id, external_uid) 복합 UNIQUE, 상태 3종 완전 분리 |
| **INQUIRIES 계열** | inquiry_id, response_id, is_latest, risk_level (LOW/MED/HIGH) | 1:N 재시도 이력 보존, (inquiry_id) WHERE is_latest=true 부분 고유 인덱스 |
| **MONTHLY_SETTLEMENTS** | settlement_id, property_id, target_month, applied_commission_rate, net_payout | (property_id, target_month) 복합 UNIQUE, **FK 제거 후 요율(0.155) 스냅샷 불변화** |
| **ACTION_ITEMS** | action_id, reservation_id, risk_level, category, status (OPEN/RESOLVED) | 규칙 기반 3단계(🔴 지금확인, 🟡 오늘확인, 🟢 자동처리) 멱등성 큐 |

#### 다. 핵심 엔티티 관계 설정 해설 (초보자용 ERD 다이어그램 & 관계 설정 이유 메모)

> 👉 [상태전이/이벤트 구조 실시간 확인](https://github.com/newrace4-arch/Host-ON-AI/blob/main/docs/state_events.md)

| 엔티티 관계 (PK ➔ FK) | 관계 카디널리티 | 왜 이렇게 관계를 설정했는가? (실무적 설계 이유) |
| --- | --- | --- |
| **HOSTS ➔ PROPERTIES** | **1 : N (일대다)** | 1명의 호스트가 독채, 게하 등 복수 숙소를 운영. **IDOR 소유권 검증의 기준**이 됨. |
| **PROPERTIES ➔ ROOMS ➔ BEDS** | **계층형 (Optional)** | 독채는 룸/침대 없이 직행 예약(NULL 허용), 게스트하우스는 룸·침대 분할 판매 완벽 지원. |
| **RESERVATIONS ➔ CLEANING_TASKS** | **1 : 1 (UNIQUE)** | 예약당 청소 1건 자동 발행(수동 생성 불가). **예약 확정 즉시 선제 생성**하여 노쇼 방지 알림. |
| **RESERVATIONS ➔ SETTLEMENTS** | **1 : N (불변 스냅샷)** | **FINANCIAL_CONFIGS와 FK를 의도적으로 끊음!** 당시 15.5% 요율을 값 복사하여 과거 장부 불변 보장. |
| **INQUIRIES ➔ RESPONSES** | **1 : N (이력 보존)** | 재답변 시 덮어쓰지 않고 행 추가. `retry_count = count - 1`로 **최대 2회(총 3회) 엄격 통제**. |
| **전체 ➔ ACTION_ITEMS** | **다대일 (단일 수렴 큐)** | 청소지연, 중복예약, 성수기방치 등 모든 위험 상황이 규칙 기반 3단계 큐(🔴🟡🟢)로 통합 수렴. |

### 4. 기술 스택 및 AI 비용·안전 통제 설계

#### 가. 확정 기술 스택 명세 (Technology Stack)

| 구분 | 적용 기술 | 선정 이유 및 역할 |
| --- | --- | --- |
| **Backend** | Python 3.11, FastAPI, SQLAlchemy 2.0, Pydantic v2 | 비동기 고성능 REST API, 엄격한 계층간 DTO 검증, 도메인 비즈니스 룰 방어 |
| **Database** | PostgreSQL 15+ (Docker 로컬 / Supabase 배포) | MariaDB 문법 오류 방지를 위해 로컬부터 동일 엔진 채택, 복합 고유 제약 및 부분 인덱스 |
| **AI / Agent** | Claude 3.5 Sonnet, LangChain | 의도·위험도·다국어 단일 통합호출(Structured Output), **애플리케이션 레벨 단일 API 호출 재시도 루프** |
| **RAG / Vector** | **PostgreSQL 15 + pgvector 확장**, HuggingFace Embeddings | `property_id` 메타데이터 필터링을 통해 타 숙소 정보 침범을 물리적으로 원천 격리 |
| **Frontend** | React 18, Vite, Tailwind CSS | 1인 호스트용 직관적 멀티 숙소 반응형 대시보드 및 Action Center 알림 큐 |
| **인프라 / 배포** | Vercel (FE), Render (BE), Supabase (DB) | 무료 티어 기반 3계층 클라우드 배포, **최초 배포 10/1 및 10/8 정식 전환** |

#### 나. 핵심 기술선택 근거

- **Property 데이터 격리 원칙 (RAG 교차오답 방지)**: 다중 숙소를 운영하는 1인 호스트 특성상 숙소 A의 이용 규칙(주차, 분리수거 등)이 숙소 B 게스트에게 안내되는 환각을 원천 차단하기 위해, 모든 지식베이스(KB) 검색 시 `property_id` 메타데이터 필터를 물리적으로 강제 격리 적용함.

- **인프라 배포 전략 (Azure 검토 후 Render 유지)**: 지원되는 Azure Cloud 크레딧 전환을 심층 검토했으나, 체험용 크레딧의 만료 및 예산 초과 리스크를 배제하고, 월 750시간 무료 인스턴스와 GitHub 연동이 검증된 Render(BE) + Supabase(DB) 스택을 최종 유지하여 인프라 안정성을 확보함.

- **Render 무료 플랜 콜드스타트 대응 전략 (강사 제안 검토 반영)**: 3계층 배포(Vercel·Render·Supabase) 중 15분 단위 슬립 현상은 Render(BE) 무료 웹서비스에만 해당한다(Vercel은 서버리스라 슬립 개념이 없고, Supabase 무료DB는 1주일 미사용 시에만 일시정지되는 별도 메커니즘). Render는 15분 미사용 시 자동 슬립되며 이후 첫 요청에 약 50초의 콜드스타트 지연이 발생한다. 이를 방지하기 위해 DB 조회가 없는 경량 헬스체크 엔드포인트(`GET /health`)를 별도로 두고, 14분 이내 간격으로 외부 무료 모니터링 도구(UptimeRobot 등)가 이 엔드포인트에 핑을 보내도록 하여 슬립을 방지한다. 다만 이는 Render의 공식 지원 기능이 아닌 외부 워크어라운드이므로, 발표 직전에는 별도로 수동 접속하여 정상 기동을 재확인하는 절차도 함께 둔다. (배포 기간을 10/1~10/12로 한정하므로 최대 288시간만 소요되어, Render 무료 한도인 월 750시간과도 충분한 여유로 충돌하지 않음을 확인함)

- **재시도 "총 3회" 정의 명확화**: 문서 전반의 "최대 총 3회"는 **호스트가 직접 트리거하는 재생성 요청 기준**(최초 1회+사용자 재생성 최대 2회)이다. 이와 별개로, Claude API가 타임아웃/장애로 응답 자체에 실패한 경우 시스템이 **자동으로 1회만 조용히 재시도**하는 절차가 있는데, 이는 사용자의 품질 불만이 아닌 인프라 장애 대응이므로 위 "3회" 카운트에는 포함시키지 않는다(최악의 경우 실제 API 호출은 4회까지 가능하나, 매 문의당 최대 4회로 상한이 명확히 유지되어 비용 폭주 위험은 없다).

#### 다. AI 비용 최적화 및 무한 루프 폭주 방지 10종 안전장치

1. 단일 통합 호출: 분류·위험도·다국어 1회 호출 (토큰 비용 60% 절감)
2. 재시도 상한 통제: 거절 시 최대 2회(총 3회) 제한, 초과 시 수동 모달
3. 로컬 RAG 검색: 숙소 매뉴얼 검색을 로컬 벡터로 수행 (LLM 비용 $0)
4. 플랫폼 예산 상한: Anthropic 콘솔 Spend Limit($10/월) 물리적 차단
5. 타임아웃 & 스텝: 호출 타임아웃 10초 및 MAX_AGENT_STEPS 방어
6. 엔드포인트 Rate Limit: FastAPI 미들웨어 기반 악의적 중복 호출 방지
7. RAG Top-K 제한: 가장 연관성 높은 3건만 프롬프트에 주입 (토큰 절약)
8. 개발 환경 응답 캐싱: 동일 질의 로컬 테스트 시 Mock 응답 반환
9. 사용량 실시간 로깅: Input/Output 토큰 실시간 DB 적재 및 모니터링
10. 키 격리 & 실발송 차단: Dev/Prod 키 분리 및 SMS 실발송은 데모 시만 활성화

- **숙소 지식 기반 다국어 응답**: 한국어, 영어, 일본어, 중국어 맞춤형 실시간 응대 및 이종 숙소 간 정보 교차 유출 차단.
- **규칙 기반 액션 센터**: AI 판단에 의존하지 않는 비즈니스 룰 기반 3단계 긴급도 분기 표출.

| 긴급도 분류 | 트리거 조건 | 처리 프로세스 |

- 평일 공백일 자동 할인: 체크인 7일 전 미예약 시 -1,500원 / 체크인 3일 전 미예약 시 -3,000원(-1%) 자동 조정.
- 주말/공휴일 자동 할증: 주말 체크인 7일 전 미예약 시 +3,000원 / 공휴일 미예약 시 +5,000원 상향 조정.
- 성수기 방치 감지 안전장치: 공휴일/연휴임에도 기본가로 M일 이상 방치 시 100% 자동조정 금지, 호스트 확인 카드(🟡 오늘 확인) 발송.

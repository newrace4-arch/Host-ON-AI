## 1. 기술 설계·AI 활용 (배점 35%)

- **[세 단위 예약을 한 테이블로]** PROPERTY/ROOM/BED 예약을 `RESERVATIONS` 하나로 표현하고 `room_id`/`bed_id`를 nullable로 두었다.
  - 근거: `backend/app/models/reservation.py:138-139`, `a457074`(9/5 초기 스키마), CLAUDE.md 「핵심 데이터 모델 원칙」
  - 발표에서 할 말: 독채 통대여와 호스텔 침대 판매를 동시에 운영하는 것이 이 프로젝트의 출발점이고, 그래서 예약 테이블을 유형별로 나누지 않고 판매단위를 컬럼으로 뒀다.

- **[EXCLUDE 3종 분리 — COALESCE 트릭 폐기]** 겹침 방지 제약을 PROPERTY/ROOM/BED 단위로 3개 분리했다. `COALESCE(room_id, 0)`으로 하나로 합치는 방식은 폐기했다.
  - 근거: CLAUDE.md 「핵심 데이터 모델 원칙」(*"COALESCE(room_id, 0) 같은 트릭은 사용 금지(데이터 오염 위험, 이미 폐기 결정됨)"*), `docs/troubleshooting.md` **1번**(*"예약 겹침방지 제약을 하나로 통합하려다 데이터 오염 위험 발견"*), 일자별 실행리스트 행 51 주의할 점
  - 발표에서 할 말: 0을 "값 없음"과 "실제 0번 ID"로 구분할 수 없어 데이터가 오염된다. 제약 하나로 줄이는 대신 셋으로 나눴다.

- **[EXCLUDE가 못 잡는 층간 충돌은 서비스가 막는다]** EXCLUDE는 같은 층끼리만 본다(독채 예약은 `room_id IS NULL`, 객실 예약은 `room_id = 5`라 서로 다른 인덱스에 들어간다). 독채↔객실↔침대 교차 충돌은 `assert_no_overlap`이 막는다.
  - 근거: `backend/app/services/reservation_service.py`의 `units_collide` 도크스트링 표, `614bb7b`(9/5), `docs/troubleshooting.md` **2번**(*"DB가 자동으로 강제한다고 설계했던 규칙이 기술적으로 불가능했음을 발견"*)
  - 발표에서 할 말: DB 제약만으로 전부 막으려다 한계를 확인하고, DB(형식 제약)와 애플리케이션(비즈니스 검증)의 책임을 나눴다.

- **[제약이 "정말 거부하는지"를 실행으로 확인]** 제약은 9/5부터 걸려 있었으나 그것이 INSERT를 실제로 거부하는지 확인한 테스트가 0건이었다. 9건을 추가했다.
  - 근거: `58a0d0b`(9/14), `backend/tests/test_exclude_constraint_behavior.py`(+254줄), devlog 2026-09-14 1절
  - 발표에서 할 말: "제약이 걸려 있다"와 "제약이 동작한다"는 다른 문장이다. 후자는 실행해 봐야 안다.

- **[LangGraph·멀티에이전트를 도입하지 않는다]** RAG 검색 후 **Claude 1회 통합 호출**로 분류+위험도+다국어+근거를 동시에 받는다. 역할을 여러 AI로 쪼개지 않는다.
  - 근거: CLAUDE.md 「기술 스택」·「하지 말아야 할 것」(*"역할을 여러 AI로 쪼개는 구조는 절대 금지 … 9/4 기준 이미 3회 이상 발견·거부됨"*), `docs/ui_design.md` 7-4절 C 플로우
  - 발표에서 할 말: 멀티스텝으로 쪼개면 호출 수만큼 비용이 붙는다. 노드 분리가 필요 없는 구조라 단일 호출로 고정했고, 외부 문서에서 되살아날 때마다 정정했다.

## 2. 서비스 구현·안정성 (30%)
